# 阶段 1：数据库迁移、事务、运行记录与幂等设计

本文对应项目优化计划的阶段 1.1 至 1.5，帮助读者从数据库结构、事务边界和并发行为三个角度理解代码。

当前完成的是数据库和服务层基础：旧聊天链路已经使用连接池、完整会话 UUID、消息 UUID 和新的消息顺序事务；`chat_runs`、幂等接纳服务已经实现，但要等阶段 1.6 的新版 HTTP 接口接入后才会被聊天请求使用。运行事件、取消接口和分页尚未实现。

## 1. 总体分层

本阶段把“修改数据库结构”和“运行期访问数据库”分开。

```text
部署阶段
  -> db_preflight.py 只读检查
  -> backup_database.py 逻辑备份
  -> Alembic upgrade 修改结构和迁移数据
  -> 启动 Flask / Gunicorn

运行阶段
  -> Route
  -> Service（跨表业务事务）
  -> Repository / DAO（单表 SQL 和状态更新）
  -> app.db（连接池、事务、慢查询计时）
  -> MySQL
```

对应代码入口：

- `zzx-ai-agent-backend/alembic.ini`：Alembic 配置。
- `zzx-ai-agent-backend/migrations/env.py`：从环境变量构造迁移连接。
- `zzx-ai-agent-backend/app/db.py`：连接池和事务上下文。
- `zzx-ai-agent-backend/app/chat_history.py`：会话、消息和摘要的数据访问。
- `zzx-ai-agent-backend/app/repositories/chat_runs.py`：运行状态机。
- `zzx-ai-agent-backend/app/repositories/idempotency.py`：幂等记录操作。
- `zzx-ai-agent-backend/app/services/chat_submission.py`：消息、run 和幂等记录的跨表原子事务。

路由层不直接拼接 SQL。现有 `auth.py`、`chat_history.py` 和 `rag_documents.py` 同时承担旧代码的 DAO 角色；新增跨表逻辑放在 `services`，避免继续把业务事务写进路由。

## 2. 为什么改用 Alembic

旧实现会在应用启动时执行 `CREATE TABLE IF NOT EXISTS`、`SHOW COLUMNS` 和 `ALTER TABLE`，存在以下问题：

1. 无法准确知道一个环境执行过哪些结构变更。
2. 多个 Web Worker 可能同时执行 DDL。
3. 结构变更和应用启动耦合，失败时难以恢复。
4. 无法在部署前完成备份、校验和审核。

现在应用启动只检查 `alembic_version`，结构未迁移时 `verify_database_schema()` 会阻止启动并提示执行 `alembic upgrade head`。RAG 目录同步仍在启动时运行，但它只同步业务数据，不再修改表结构。

## 3. 两个迁移版本

### 3.1 `20260918_0001`：legacy baseline

第一版同时兼容两类环境：

- 空数据库：创建项目原有的用户、聊天和 RAG 表。
- 已运行旧代码的数据库：已有表不重复创建，把现状纳入 Alembic 管理。

它的 `downgrade()` 不删除表，因为 baseline 可能只是接管升级前就存在的生产表。

### 3.2 `20260918_0002`：阶段 1 数据完整性

第二版负责：

- 归档历史孤儿数据。
- 增加 `next_message_order` 和 `version`。
- 为历史消息生成完整 `message_id`。
- 增加 `client_message_id`。
- 增加唯一约束、索引和外键。
- 创建 `chat_runs` 和 `idempotency_records`。

MySQL DDL 不是完整事务型操作，因此升级前必须备份，不能假设迁移失败后所有 `ALTER TABLE` 都会自动回滚。

## 4. 历史 ID 与孤儿数据兼容

### 4.1 不重写旧 session_id

旧代码使用 `str(uuid.uuid4())[:8]`。直接重写会同时影响 URL、消息、摘要和潜在外部引用，因此采用扩展式兼容：

- 已有 8 位 session_id 原样保留。
- 新会话使用完整 36 位 UUID。
- 字段继续使用 `VARCHAR(100)`，同时容纳两种格式。

### 4.2 内部主键和公开标识并存

| 表 | 内部主键 | 对外业务标识 |
|---|---|---|
| sessions | `id INT` | `session_id VARCHAR(100)` |
| chat_messages | `id INT` | `message_id VARCHAR(36)` |
| chat_runs | UUID 本身作为主键 | `id VARCHAR(36)` |

保留整数主键降低迁移风险；接口不应依赖内部自增值。

### 4.3 孤儿数据归档

迁移前存在 `sessions.user_id` 找不到用户的记录。迁移按以下流程处理：

```text
查找无主 sessions
  -> 关联消息写入 migration_orphan_records
  -> 关联摘要写入 migration_orphan_records
  -> session 自身写入 migration_orphan_records
  -> 从活动表移出这些记录
  -> 建立外键
```

归档表的 `payload` 保存原行 JSON，`source_table` 和 `source_key` 标识来源。当前本地迁移实际归档了 2 个无主会话和 10 条消息；迁移前另有完整逻辑备份。

## 5. 外键与删除策略

```text
users
  ├─ sessions                 ON DELETE CASCADE
  │    ├─ chat_messages       ON DELETE CASCADE
  │    ├─ chat_summaries      ON DELETE CASCADE
  │    └─ chat_runs           ON DELETE CASCADE
  └─ idempotency_records      ON DELETE CASCADE

chat_messages.message_id
  ├─ chat_runs.user_message_id       ON DELETE RESTRICT
  └─ chat_runs.assistant_message_id  ON DELETE SET NULL
```

- 删除会话时，消息、摘要和运行记录由 MySQL 级联清理。
- run 必须保留发起它的用户消息，因此用户消息使用 `RESTRICT`。
- 助手消息允许因为异常恢复或数据修复而缺失，因此使用 `SET NULL`。
- `delete_session()` 只删除会话主记录，关联清理由外键完成。

## 6. 索引与唯一约束

### sessions

- `session_id` 唯一。
- `idx_user_chat_type(user_id, chat_type)` 支持会话列表。
- `idx_sessions_user_updated(user_id, updated_at, id)` 为后续游标分页准备。

### chat_messages

- `message_id` 唯一。
- `UNIQUE(session_id, msg_order)` 是顺序的数据库最后防线。
- `UNIQUE(session_id, client_message_id)` 防止同一会话重复接纳同一客户端消息。

`client_message_id` 暂时允许为空，以兼容尚未传入该字段的旧 SSE；阶段 1.6 新接口会要求必填。

### chat_runs

- `idx_chat_runs_lookup(user_id, session_id, status, created_at)` 支持组合查询。
- `idx_chat_runs_session_created(session_id, created_at)` 支持执行历史。

### idempotency_records

- `UNIQUE(user_id, endpoint, idempotency_key)` 定义幂等作用域。
- `expires_at` 为后续清理任务提供索引。
- `(resource_type, resource_id)` 支持从 run 反查幂等记录。

消息表原有普通 `(session_id, msg_order)` 索引与新唯一索引部分重叠，暂时保留兼容；后续根据真实 `EXPLAIN` 决定是否精简。

## 7. 连接池设计

项目仍用 PyMySQL 执行原有 `%s` SQL，但连接生命周期由 SQLAlchemy Engine 管理：

- Engine 提供 QueuePool 和 `pool_pre_ping`。
- `raw_connection()` 取得底层连接。
- `_PooledDictConnection` 保持旧代码需要的 `DictCursor`。
- `close()` 把连接归还池，而不是每次关闭物理连接。

本阶段没有强行改成 ORM，因为当前核心问题是连接数量、事务边界和并发正确性。一次性改 ORM 会扩大风险。

连接池保存在 Flask `app.extensions`，所以每个 Gunicorn Worker 各有一份：

```text
理论最大连接数
= Worker 数 × (MYSQL_POOL_SIZE + MYSQL_MAX_OVERFLOW)
```

当前默认 1 个 Worker，池大小 8、overflow 4，单进程峰值为 12 条连接。

| 配置 | 默认值 | 作用 |
|---|---:|---|
| MYSQL_POOL_SIZE | 8 | 常驻池容量 |
| MYSQL_MAX_OVERFLOW | 4 | 池满后的临时连接 |
| MYSQL_POOL_TIMEOUT | 10 秒 | 等待可用连接的上限 |
| MYSQL_POOL_RECYCLE | 1800 秒 | 回收长期连接 |
| MYSQL_CONNECT_TIMEOUT | 5 秒 | 建连超时 |
| MYSQL_READ_TIMEOUT | 30 秒 | 读取超时 |
| MYSQL_WRITE_TIMEOUT | 30 秒 | 写入超时 |
| MYSQL_SLOW_QUERY_MS | 500 毫秒 | 慢查询阈值 |

慢查询只记录操作类型和耗时，不记录 SQL 参数，避免泄露密码、Token 或对话内容。

## 8. connection 与 transaction

只读操作使用：

```python
with connection() as conn:
    ...
```

它只保证连接归还，不自动提交。

写操作使用：

```python
with transaction() as conn:
    ...
```

```text
借连接
  -> 正常结束：commit
  -> 任意 Exception：rollback 并继续抛出
  -> finally：归还连接
```

需要原子性的流程必须共用同一个 `conn`。因此 `save_message()` 支持外部传入连接：单独调用时自己开启事务，被消息接纳服务调用时复用外层事务。

## 9. 消息顺序事务

旧算法 `MAX(msg_order)+1` 把顺序状态隐含在消息表里。现在由 `sessions.next_message_order` 显式保存下一条序号：

```text
BEGIN
  SELECT next_message_order
  FROM sessions
  WHERE user_id=? AND session_id=?
  FOR UPDATE

  INSERT chat_messages(..., msg_order=next_message_order)

  UPDATE sessions
  SET next_message_order=next_message_order+1,
      updated_at=UTC_TIMESTAMP(6)
COMMIT
```

同一会话的写入因会话行锁而串行分配序号，不同会话仍能并发。任一步失败都会回滚，序号不会被提前消耗；唯一约束负责拦截绕过标准函数的重复顺序写入。

## 10. chat_runs 状态机

用户消息表达内容，`chat_run` 表达对该消息的一次 AI 执行。两者分开后才能表达“消息已接收但尚未执行”“执行失败”或“已取消”。

字段可以分为：

- 标识与归属：`id`、`user_id`、`session_id`。
- 消息：`user_message_id`、`assistant_message_id`。
- 状态：`status`、`version`、`retry_count`。
- 模型：`model`、`agent_type`。
- 追踪：`request_id`。
- 错误：`error_code`、`error_message`。
- 用量：prompt/completion/total tokens、estimated_cost。
- 时间：created/started/finished/updated at。

允许转换：

```text
queued  -> running   -> succeeded
                   \-> failed
                   \-> timed_out
queued  -> cancelled
running -> cancelled
```

更新条件同时检查旧状态和 version：

```sql
WHERE id=? AND user_id=? AND status=? AND version=?
```

成功时执行 `version=version+1`。例如 Worker A 把 `queued/version=1` 更新为 `running/version=2` 后，Worker B 再用旧版本领取只会影响 0 行。这种比较并交换避免多个 Worker 同时执行或完成一个 run。

Python 的 `ALLOWED_TRANSITIONS` 拒绝明显非法的转换，数据库 `CHECK` 防止非法状态字符串，条件更新负责真正的并发裁决。

## 11. 幂等作用域与请求哈希

唯一范围是：

```text
(user_id, endpoint, idempotency_key)
```

因此不同用户或不同接口可以安全复用同一个 key。

`request_hash` 是以下规范化 JSON 的 SHA-256：

```json
{
  "agent_type": "chain",
  "client_message_id": "...",
  "content": "...",
  "session_id": "..."
}
```

JSON 使用固定字段、排序键、紧凑分隔符和 UTF-8。`request_id` 不进入哈希，因为网络重试会产生新的诊断编号；`model` 当前由服务端决定；`endpoint` 已属于唯一作用域。

## 12. 原子消息接纳流程

`create_chat_submission()` 负责“只接纳一次”，不负责执行模型。

首次请求：

```text
校验 client_message_id 和 Idempotency-Key
  -> 计算 request_hash
  -> BEGIN
       INSERT idempotency_records(status=processing)
       SELECT session ... FOR UPDATE
       INSERT user message
       UPDATE session order/time
       INSERT chat_run(status=queued)
       UPDATE idempotency record(status=completed, response_body=IDs)
     COMMIT
  -> 返回 message_id、run_id、queued
```

所有写入共用一个连接。任何一步失败，幂等记录、消息、顺序、会话时间和 run 全部回滚。

### 相同 key、相同请求

并发请求插入相同唯一键时 MySQL 返回 1062。代码会退出并回滚冲突事务，再用全新事务读取已有记录、比较哈希并返回首次请求保存的响应。

必须换新事务：测试验证过，如果在发生重复键冲突的事务中继续 `SELECT ... FOR UPDATE`，高并发下容易形成锁等待和死锁。

### 相同 key、不同请求

如果 key 相同但哈希不同，抛出 `IdempotencyConflict`。阶段 1.6 会映射成 HTTP 409。

### client_message_id 的第二道保护

即使调用方换了新的 Idempotency-Key，只要仍使用相同 `client_message_id`，`UNIQUE(session_id, client_message_id)` 仍会阻止重复消息。

- Idempotency-Key 用于返回首次请求的稳定结果。
- client_message_id 唯一约束用于保护消息实体不重复。

阶段 1.6 还需把 client_message_id 冲突映射为稳定业务响应。

## 13. 有限重试策略

消息接纳服务只对 MySQL 1205（锁等待超时）和 1213（死锁）做最多 3 次短退避重试，并加入随机抖动。

它能够安全重试，是因为幂等唯一记录在消息和 run 之前创建，所有尝试会收敛到同一业务结果。普通写操作没有这个前提，不会统一套用“出错就重试”，否则可能重复执行。

## 14. 注册并发冲突

旧流程先查询用户名再插入，两个并发请求可能同时查到不存在。现在直接依赖数据库 `UNIQUE(username)`：插入成功即注册成功，MySQL 1062 会回滚并返回 `USERNAME_ALREADY_EXISTS / HTTP 409`。数据库而不是应用层查询承担最终裁决。

## 16. 测试如何验证设计

`tests/test_stage1_database.py` 使用真实 MySQL：

1. 20 个线程用相同幂等键并发提交。
2. 最终只有一条用户消息和一个 run。
3. 所有调用拿到同一 run_id。
4. next_message_order 正确递增。
5. 相同 key、不同内容产生冲突。
6. queued/version=1 只能被一个更新变为 running/version=2。
7. succeeded -> running 被状态机拒绝。

CI 增加 MySQL 8，先在空库执行迁移，再运行测试。本地需要显式设置 `RUN_MYSQL_INTEGRATION=1`，避免普通单元测试误写开发库；测试创建随机临时用户并在结束时级联清理。

## 17. 当前边界和下一步

已经生效：

- 新会话使用完整 UUID。
- 旧 SSE 写入的用户和助手消息使用新顺序事务及 message_id。
- 消息写入更新会话 `updated_at`。
- 现有 MySQL 辅助方法通过兼容入口使用连接池。
- 会话删除依赖外键级联。

已经实现但尚未由 HTTP 使用：

- `create_chat_submission()`。
- Idempotency-Key/request_hash 处理。
- queued chat_run 创建和 run 条件状态转换。

旧接口把问题放在 GET SSE 参数里，一个请求同时承担接纳和执行。直接把幂等服务塞回旧接口仍无法建立清晰的重连语义，因此留到阶段 1.6 一次性切换为“POST 接纳，再按 run_id 订阅”。

阶段 1.6 需要完成：

1. 新增 `POST /api/sessions/{session_id}/messages`。
2. 将幂等冲突映射为 HTTP 409。
3. 新增 run 查询、事件订阅和取消接口。
4. 模型执行通过条件更新领取 queued run。
5. 助手消息和 run 成功状态在同一事务落库。
6. 前端改为先 POST，再按 run_id 订阅。

其他预留边界：

- `expires_at` 已有索引，但尚无定时清理任务。
- `locked_until` 和幂等 `failed` 为异常恢复预留。
- 尚未持久化 SSE delta，断线续传属于阶段 2。
- 部分历史 `DATETIME` 仍依赖 MySQL 会话时区，统一 UTC API 输出属于阶段 1.7。
