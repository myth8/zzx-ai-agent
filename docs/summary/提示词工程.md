## 二、System Prompt（角色设定）

### 2.1 AI 恋爱大师（Chain 模式）

**文件位置**：`app/routes/love_app.py`

```python
SYSTEM_PROMPT = (
    "You are AI Love Master, a warm relationship advisor.\n"
    "Answer in Chinese. Be empathetic and give practical advice."
)
```

**Prompt 元素分析：**

| 元素 | 内容 | 作用 |
| :--- | :--- | :--- |
| **角色定义** | "a warm relationship advisor" | 设定 AI 的身份为情感顾问，而非通用助手 |
| **温度描述** | "warm" | 暗示回复语气应温暖、亲切 |
| **语言约束** | "Answer in Chinese" | 强制输出中文，确保用户体验 |
| **风格指引** | "be empathetic" | 强调共情能力，适合情感咨询场景 |
| **内容方向** | "give practical advice" | 暗示回复应包含可执行的建议，而非纯安慰 |

### 2.2 AI 超级智能体（Agent 模式）

**文件位置**：`app/routes/manus.py`

```python
SYSTEM_PROMPT = (
    "You are AI Super Agent, a versatile assistant."
    "Answer in Chinese. Be clear, structured, and helpful."
)
```

**Prompt 元素分析：**

| 元素 | 内容 | 作用 |
| :--- | :--- | :--- |
| **角色定义** | "a versatile assistant" | 设定为全能助手，而非领域专家 |
| **语言约束** | "Answer in Chinese" | 中文输出（与恋爱大师一致） |
| **风格指引** | "be clear, structured" | 强调清晰、结构化，适合专业问答 |
| **价值导向** | "helpful" | 引导 AI 以解决问题为核心 |

### 2.3 设计对比

| 维度 | AI 恋爱大师 | AI 超级智能体 |
| :--- | :--- | :--- |
| **角色定位** | relationship advisor（顾问） | versatile assistant（助手） |
| **情感色彩** | warm, empathetic（温暖共情） | clear, structured（清晰结构化） |
| **输出导向** | practical advice（实用建议） | helpful（解决问题） |
| **长度** | 1 行 | 1 行 |

**技巧**：通过极简的角色设定就能有效区分两种 AI 的输出风格，说明角色定义（Role Prompting）是 Prompt Engineering 中性价比最高的技巧之一。

## 三、ReAct Agent 模板

**文件位置**：`app/llm/agent.py` 中的 `AGENT_TEMPLATE`

这是整个项目中最复杂、最核心的提示词模板。它同时服务于 ReAct 推理循环、工具调用和 Skills 路由三大机制。

### 3.1 完整模板结构分解

```
┌──────────────────────────────────────────────────────┐
│ {system_prompt}          ← 外部注入的角色指令        │
├──────────────────────────────────────────────────────┤
│ Skills 路由指令                                      │
│  • 什么是 Skills                                     │
│  • CRITICAL ROUTING RULE（自动路由判断条件）          │
│  • 四步决策流程（Step A → B → C → D）               │
│  • IMPORTANT：不需用户显式触发                       │
├──────────────────────────────────────────────────────┤
│ 可用工具列表                                         │
│  {tools}               ← LangChain 自动填充          │
├──────────────────────────────────────────────────────┤
│ 严格格式规则                                         │
│  • 两种输出模式                                       │
│  • 6 条 CRITICAL RULES                               │
├──────────────────────────────────────────────────────┤
│ 示例（Zero-shot Example）                            │
│  • 完整演示一次工具调用+最终答案生成                   │
├──────────────────────────────────────────────────────┤
│ 用户输入 + Agent Scratchpad                          │
│  {input} + {agent_scratchpad}                       │
└──────────────────────────────────────────────────────┘
```

### 3.2 Skills 路由指令

```text
You have access to a set of advanced "Skills" — these are specialized, multi-step workflows
for handling specific domain tasks (e.g., romantic confession generation, conflict resolution,
trust repair).

Your available skill-related tools are:
- `list_skills` — lists all available skills and their brief descriptions.
- `read_skill` — retrieves the full instruction body of a specific skill by its name.

CRITICAL ROUTING RULE — HOW TO USE SKILLS AUTOMATICALLY:
When a user's request falls into any of the following categories, DO NOT respond with a
generic answer or force the user to type an explicit trigger command. Instead, you MUST
proactively consider using a skill:
1. The request is vague, complex, or creative in nature, and the user does not specify
   a concrete tool or format.

Your decision flow:
Step A — Identify the domain. If it matches the above, call `list_skills` to check
         if a relevant skill exists.
Step B — If a matching skill is found (e.g., "romantic_confession_generator"),
         call `read_skill` with its exact name to load its full instructions.
Step C — Execute the skill's body step by step. This may include calling other base
         tools (like `get_time`) as required by the skill.
Step D — Produce the final output strictly according to the skill's format and
         length requirements.

IMPORTANT — You DO NOT need the user to repeat any special command like "[时刻浪漫表白]".
Once the skill is loaded, act as if it is already activated, and follow its internal
workflow precisely. This makes the experience seamless for the user.
```

**设计技巧：**

| 技巧 | 说明 |
| :--- | :--- |
| **概念先定义** | 先解释 "What is Skills"，再说明如何使用 |
| **决策流程化** | 用 Step A → B → C → D 将模糊的"判断-行动"转化为可执行的伪代码 |
| **CRITICAL 标记** | 大写关键字强调必须遵守的规则 |
| **DO NOT 约束** | 明确告诉 AI 什么不该做（"不要用通用回答"、"不要强迫用户触发"） |
| **具体化描述** | 不是简单说"用技能"，而是给出具体场景示例 |

### 3.3 格式约束

```text
STRICT FORMAT RULES - YOU MUST FOLLOW THESE EXACTLY:
You must output EXACTLY ONE of the following two patterns in each response:

=== Pattern 1 - Call a tool ===
Thought: (your reasoning)
Action: (tool name, exactly one of [{tool_names}])
Action Input: (input for the tool)

=== Pattern 2 - Give the final answer ===
Thought: (your reasoning)
Final Answer: (your complete answer to the user)

CRITICAL RULES:
- "Final Answer:" MUST appear at the very end, on its own line.
- Never output explanatory text before or after the patterns above.
- Never output Chinese text outside of "Final Answer:".
- The "Action:" line must include only the tool name.
- The "Action Input:" line must include only the tool input.
- After "Final Answer:", do NOT add any more text.
```

**设计技巧：**

| 技巧 | 说明 |
| :--- | :--- |
| **双模式约束** | 明确告诉 AI 只有两种输出格式，没有第三种选择 |
| **格式模板化** | 用等号分隔清晰标示两种模式，便于 LLM 理解和遵循 |
| **CRITICAL RULES 枚举** | 6 条规则逐一列出，每条解决一个常见的格式错误 |
| **否定指令** | "Never output..."、"do NOT add..." 比单纯的正向指令更有效 |
| **工具名占位符** | `[{tool_names}]` 让 LangChain 自动填入实际可用的工具名 |

### 3.4 零样本示例

```text
=== Example ===
Question: What time is it?
Thought: I need to check the current time.
Action: get_time
Action Input: (none)
Observation: 2026-07-16 10:00:00
Thought: I have the time now.
Final Answer: Current time is 2026-07-16 10:00.
```

**技巧**：在 Prompt 末尾提供一个完整的、可运行的示例（Few-shot in-context learning），展示从 Question → Thought → Action → Observation → Final Answer 的完整链路。示例使用的工具是最简单的 `get_time`，确保 LLM 能零门槛理解格式。

### 3.5 安全约束

Agent 模板中还隐含着多层安全设计：

| 技巧 | 实现方式 |
| :--- | :--- |
| **语言隔离** | "Never output Chinese text outside of Final Answer" 确保 Thought 和 Action 输出英文，Final Answer 输出中文，避免解析混乱 |
| **格式自愈** | `handle_parsing_errors=True` 让 AgentExecutor 在格式异常时自动重试 |
| **循环控制** | `max_iterations=15`、`max_execution_time=90` 从执行器层面防止失控 |
| **长度控制** | `early_stopping_method="generate"` 在 Agent 无法继续时强制输出 |

## 四、工具描述（Tool Docstring）

工具的描述文本（docstring）是 LLM 决定「何时调用哪个工具」的关键依据。每条描述本质上就是一个微型的 Prompt。

### 4.1 全部工具描述一览

```python
@tool
def get_time():
    """Get current date and time. Use when user asks about time."""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

@tool
def calc(expr: str):
    """
    Calculate a math expression.
    Input: expression string like "2 + 3 * 4" or "sqrt(16)".
    """
    ...

@tool
def get_now_weather(location: str) -> dict:
    """
    Query real-time weather information for a specified location.

    Args:
        location: The location to query, supports city name (e.g., "Shanghai"),
                  city pinyin (e.g., "shanghai"), or coordinates (e.g., "31.23:121.47").

    Returns:
        A string containing the real-time weather information...
    """
    ...

@tool
def rag_search(query: str) -> str:
    """
    Search the love-and-relationship knowledge base.
    Use this when the user asks questions about dating, marriage, breakups,
    relationship advice, emotional issues, or similar topics.
    Input: the user's question or keywords.
    """
    ...

@tool
def list_skills():
    """列出所有可用的技能模块名称和简介。"""
    ...

@tool
def read_skill(skill_name: str):
    """读取指定技能的完整内容，输入技能名称。"""
    ...
```

### 4.2 描述设计技巧

| 技巧 | 示例 | 作用 |
| :--- | :--- | :--- |
| **场景指引** | `get_time`: "Use when user asks about time" | 告诉 LLM 什么时候该用这个工具 |
| **参数示例** | `calc`: "like '2 + 3 * 4' or 'sqrt(16)'" | 让 LLM 理解参数格式 |
| **支持的格式** | `get_now_weather`: "city name, pinyin, or coordinates" | 防止 LLM 传入不支持的值 |
| **返回说明** | `get_now_weather`: "A string containing..." | 让 LLM 知道能得到什么 |
| **领域限定** | `rag_search`: "love-and-relationship knowledge base" | 精确划定搜索范围 |
| **场景枚举** | `rag_search`: "dating, marriage, breakups, relationship advice" | 举例说明使用场景 |
| **中文描述** | `list_skills`: 中文描述 | Skills 工具用中文描述，与 Skills 文档一致 |

### 4.3 安全兜底设计

```python
@tool
def get_now_weather(location: str) -> dict:
    try:
        result = asyncio.run(weather_tool.ainvoke({"location": location}))
        return str(result)
    except Exception as e:
        return "未获取到天气数据"   # ← 友好的错误提示，不暴露技术细节

@tool
def calc(expr: str):
    try:
        result = eval(expr, {"__builtins__": {}}, {})
        return str(result)
    except Exception as e:
        return f"Error: {e}"        # ← 错误时告诉 LLM 发生了什么
```

工具自身的错误不在工具中处理，而是返回错误文本给 LLM，由 LLM 决定是重试还是告知用户。这种设计避免了工具崩溃导致 Agent 整体失败。

## 五、对话摘要 Prompt

**文件位置**：`app/chat_history.py` 中的 `update_summary` 函数

### 5.1 完整 Prompt

```python
prompt = ChatPromptTemplate.from_messages([
    ("human", (
        "请将以下对话压缩为中文摘要，只保留以下信息：\n"
        "1. 用户的身份、兴趣、目标\n"
        "2. 用户提出的主要问题或请求\n"
        "3. AI给出的关键回答或建议\n"
        "不要重复对话细节，只做概括。\n\n"
        "当前摘要：\n{summary}\n\n"
        "新的对话行：\n{new_lines}\n\n"
        "新的摘要（不超过500字）："
    )),
])
```

### 5.2 Prompt 设计分析

**三要素提取策略：**

| 要素编号 | 提取内容 | 信息类型 | 保留意义 |
| :--- | :--- | :--- | :--- |
| 1 | 用户的身份、兴趣、目标 | 长期静态信息 | 保持对用户的整体认知 |
| 2 | 用户提出的主要问题或请求 | 短期动态信息 | 记录本轮对话的核心诉求 |
| 3 | AI 给出的关键回答或建议 | 决策信息 | 保留已给出的解决方案 |

**增量更新设计：**

```
当前摘要: {summary}     ← 之前 N 轮对话的浓缩（可能为空）
新的对话行: {new_lines} ← 最近 20 条消息（格式：用户/AI）

输出: 新的摘要          ← 融入了新信息的更完整摘要
```

**约束指令：**

| 指令 | 作用 |
| :--- | :--- |
| "请将以下对话压缩为中文摘要" | 语言约束 + 任务定义 |
| "只保留以下信息" | 信息筛选（限制输出范围） |
| "不要重复对话细节，只做概括" | 质量要求（拒绝逐条摘要） |
| "不超过500字" | 长度约束 |

### 5.3 增量更新 vs 全量重写的对比

| 方式 | Token 消耗 | 信息完整性 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **全量重写** | 高（每次传入全部消息） | 完整 | 初次生成或摘要质量重置 |
| **增量更新（本项目）** | 低（仅传入已有摘要+最近消息） | 高 | 长对话持续更新 |

## 六、Skills 技能模板

**文件位置**：`skills/romantic_confession_generator.md`

Skills 模板本质上是一个「为 LLM 编写的可执行文档」，结构如下：

### 6.1 Front Matter

```yaml
---
name: romantic_confession_generator
description: Trigger this skill by entering the command "[时刻浪漫表白]"...
---
```

- `name`：技能名称，用于 `read_skill` 工具检索
- `description`：技能描述，用于 `list_skills` 工具展示

### 6.2 正文结构

**第 1 节：获取时间的诗意坐标**

```
First, you must call the `get_time` tool to obtain the following precise information:
- Current date (year, month, day)
- Current time (hour, minute)

These data are not cold numbers; they are the core material...
```

- 明确要求调用特定工具
- 解释工具数据的"诗意意义"，引导 LLM 超越机械化使用

**第 2 节：时间意象的情感映射**

```markdown
| Time Slot | Poetic Transformation (Example) |
| :--- | :--- |
| Early morning (5:00-9:00) | The first light of dawn... |
| Midday (11:00-14:00)     | The blazing sun...        |
| Dusk (17:00-19:00)       | The gradual shift of sunset... |
| Late night (22:00-5:00)  | The coolness of moonlight... |
```

- 用表格将时间映射到情感意象
- 这种结构化映射在传统编程中是枚举 switch，在 Prompt 中是"参考表"

**第 3 节：四段式结构**

```
- Paragraph 1 (Opening · Freezing the Moment): 直接陈述当前时间
- Paragraph 2 (Immersion · Natural Association): 将时间观察投射到情感
- Paragraph 3 (Climax · Core Confession): 核心告白，赋予时间独特性
- Paragraph 4 (Hope · Future Invitation): 行动邀约或未来承诺
```

- 将创意写作分解为 4 个可执行的步骤
- 每段都有明确的"目的说明"，不止是结构描述

**第 4 节：示例输出**

提供了一段约 200 字的完整中文范文，作为少样本（Few-shot）参考，让 LLM 理解期望的输出风格和质量。

**第 5 节：微调建议**

```markdown
- Avoid clichés: 必须使用 get_time 返回的真实数据
- Length control: 严格保持 180-220 字
- Consistent style: 保持"深情、细腻、略带文艺"的基调
- Alternative for late night: 00:00-04:00 时调整语气
- Language requirement: MUST be Simplified Chinese
```

### 6.3 渐进式暴露设计

Skills 的设计核心是**渐进式暴露（Progressive Disclosure）**：

```
第 1 层（名称）: Agent 调用 list_skills → 看到技能名和简介
第 2 层（正文）: Agent 调用 read_skill → 获取完整指令
第 3 层（执行）: Agent 逐段执行指令 → 调用工具 → 生成输出
```

这种设计避免了在 Agent Prompt 中塞入全部技能指令导致上下文爆炸，实现按需加载。

## 七、RAG 文档结构

**文件位置**：`documents/dating.md` 等

### 7.1 Front Matter（YAML 元数据）

```yaml
---
title: 恋爱常见问题 - 恋爱篇
status: 恋爱中
category: 情感解惑
---
```

- 作为文档的结构化元数据
- 在 RAG 检索中可以用于过滤和分类

### 7.2 文章结构

```markdown
# 恋爱篇：从"我喜欢你"到"我们好好相处"

## 1. 我们经常吵架，是不是说明不合适？

> 关键词：冲突处理、沟通技巧、倾听

吵架本身不意味着不合适，**不会吵架才意味着问题**。恋爱中的冲突往往源于沟通不畅...
```

- 大标题 `#` 作为文档主题
- 二级标题 `##` 作为问题标题（按此切分段落）
- `>` 关键词行突出核心概念
- `**加粗**` 强调关键建议

### 7.3 作为 Prompt 的设计

RAG 文档本身虽然不直接被 LLM 作为 Prompt 读取，但经过 Chunk 切分后，每个 Chunk 被注入到 LLM 的上下文中。因此文档的结构（标题、关键词、分段）直接影响 RAG 检索质量和 LLM 的理解效果。

## 八、对话上下文注入格式

**文件位置**：`app/chat_history.py` 中的 `build_context`

### 8.1 注入格式

```text
【对话摘要】
用户是一位 25 岁的程序员...
AI 建议了有效沟通的技巧...

【最近对话】
用户: 我女朋友总说我不会说话，怎么办？
AI: 这其实是很多人在感情中都会遇到的困扰...
用户: 能不能举个例子？
AI: 当然可以。比如...
```

### 8.2 设计技巧

| 技巧 | 说明 |
| :--- | :--- |
| **双层结构** | 摘要（长期记忆）+ 最近对话（短期记忆），兼顾广度和精度 |
| **结构化标签** | `【对话摘要】` 和 `【最近对话】` 作为标签，帮助 LLM 快速定位信息 |
| **角色前缀** | `用户:` 和 `AI:` 清晰区分消息来源 |
| **空值处理** | 无摘要时只传递最近对话，无最近对话时只传递摘要 |

### 8.3 注入方式对比

| 模式 | 注入方式 | 代码 |
| :--- | :--- | :--- |
| **Chain** | 通过 `{history}` 变量注入 human message | `human_template = "【对话历史】\n{history}\n\n---\n\n{input}"` |
| **Agent** | 通过追加字符串到 system_prompt | `system_prompt + "\n\n【对话历史】\n" + context` |

两种注入方式达到的效果一致，只是由于 Chain 和 Agent 的 Prompt 模板结构不同而选择了不同的实现路径。

### 9.3 关键经验总结

1. **角色 Prompt 性价比最高**：仅需一行角色定义，就能显著改变 LLM 的输出风格和内容倾向。

2. **格式约束比内容约束更有效**：告诉 LLM "你怎么输出"比"你输出什么"更容易遵循。Agent 模板的 6 条格式规则几乎覆盖了所有常见的格式错误。

3. **否定指令比正向指令更精准**："不要输出中文"比"请输出英文"更有效，因为 LLM 在否定指令上犯错的可能性更低。

4. **示例比规则更有说服力**：一个完整的 `What time is it?` 示例比 10 条格式规则更能让 LLM 理解期望的输出。

5. **渐进式暴露是长上下文的解药**：将完整指令放在外部文档中，通过运行时按需加载（list_skills → read_skill），避免了 Prompt Template 的无限膨胀。

6. **增量更新胜过全量重写**：在摘要生成场景中，基于已有摘要追加新内容的策略比每次重新生成全部消息的摘要节省 50%-80% 的 token。

7. **结构化是 Prompt 工程的基础**：无论是表格映射、四段式结构还是双模式模板，良好的结构设计都能显著提升 LLM 的理解和执行准确率。
