> 本文档详细阐述 ZZX-AI 超级智能体中的对话连续性保障机制：多轮对话（Multi-turn Conversation）、持久化记忆（Persistent Memory）和对话摘要（Dialogue Summarization）。分别从概念、作用、实现思路、实现效果四个维度展开，并在最后分析三者的协作关系与整体数据流。

## 一、多轮对话

### 1.1 概念

多轮对话是指 AI 系统能够感知并利用对话历史，使得后续的回复能够参考之前交流内容的能力。与单轮"一问一答"不同，多轮对话中的 AI 能够理解代词指代（如"刚才说的那个"）、跟踪话题变迁、维持角色设定的一致性。

本项目的多轮对话实现基于 **session_id**（会话标识符）驱动：

```
用户发送第 N 条消息
  → 提取 session_id
  → 从 MySQL 加载该会话的历史消息和摘要
  → 构造上下文窗口传入 LLM
  → LLM 基于完整上下文生成回复
  → 将新消息保存到 MySQL
```

### 1.2 作用

- **上下文连贯**：AI 能引用之前对话中的信息（如"你刚才提到..."），避免重复提问和回答
- **话题跟踪**：用户可以在同一会话中切换话题，AI 保持对语境的感知
- **角色一致**：AI 的角色设定（恋爱大师 / 超级智能体）在整轮对话中保持一致
- **后续延续**：用户可以关闭页面后再次打开同一会话，继续之前的对话

### 1.3 实现思路

**Agent 模式**（`app/routes/manus.py`）：

```python
@manus_bp.route("/api/ai/manus/chat")
def chat():
    message = request.args.get("message", "")
    session_id = request.args.get("session_id", "")

    context = ""
    if session_id:
        # 步骤 A：构建上下文（摘要 + 最近消息）
        context = build_context(session_id)
        # 步骤 B：保存用户消息
        save_message(session_id, "user", message)

    prompt = SYSTEM_PROMPT
    if context:
        prompt = SYSTEM_PROMPT + "\n\n【对话历史】\n" + context

    executor = create_agent(prompt, middleware=[...], extra_tools=[...])
    # 步骤 C：流式响应（stream_agent 内部会在流结束后保存 assistant 消息并更新摘要）
    return sse_response(stream_agent, executor, message, session_id, llm)
```

**Chain 模式**（`app/routes/love_app.py`）：

```python
@love_bp.route("/api/ai/love_app/chat/sse")
def chat():
    message = request.args.get("message", "")
    session_id = request.args.get("session_id", "")

    context = ""
    if session_id:
        context = build_context(session_id)
        save_message(session_id, "user", message)

    chain = make_chain(SYSTEM_PROMPT, context)
    return sse_response(stream_chain, chain, message, context, session_id, llm)
```

**完整六步流程：**

| 步骤 | 位置 | 动作 | 说明 |
| :--- | :--- | :--- | :--- |
| A | 路由处理函数 | `build_context(session_id)` | 从 MySQL 加载会话摘要 + 最近 50 条消息，构造上下文字符串 |
| B | 路由处理函数 | `save_message(session_id, "user", message)` | 将用户消息保存到 chat_messages 表 |
| C | 路由处理函数 | 将 context 混入 system prompt | 上下文注入到 LLM 的输入中 |
| D | stream_agent / stream_chain | 逐 token/事件流式输出 | LLM 生成回复并实时推送到前端 |
| E | stream_agent / stream_chain 结尾 | `save_message(session_id, "assistant", final_answer)` | 保存 AI 回复到 chat_messages 表 |
| F | stream_agent / stream_chain 结尾 | `update_summary(session_id)` | 判断是否需要更新对话摘要 |

#### 1.3.3 上下文构建函数

`build_context` 是连接持久化记忆和 LLM 调用的桥梁：

```python
# app/chat_history.py
def build_context(session_id):
    """构建包含摘要和最近消息的上下文字符串。"""
    summary = load_summary(session_id)
    recent = load_recent_messages(session_id, RECENT_LIMIT)  # 最近 50 条

    parts = []
    if summary:
        parts.append(f"【对话摘要】\n{summary}")

    if recent:
        lines = ["【最近对话】"]
        for msg in recent:
            prefix = "用户" if msg["role"] == "user" else "AI"
            lines.append(f"{prefix}: {msg['content']}")
        parts.append("\n".join(lines))

    return "\n\n".join(parts)
```

**上下文示例输出：**

```
【对话摘要】
用户是一位 25 岁的程序员，正在经历恋爱中的沟通问题。AI 建议了有效沟通的技巧和如何在争吵后修复关系的具体步骤。

【最近对话】
用户: 我女朋友总说我不会说话，怎么办？
AI: 这其实是很多人在感情中都会遇到的困扰。有效沟通的关键不在于说得多，而在于...
用户: 能不能举个例子？
AI: 当然可以。比如当她抱怨工作累时，与其说"那你就别做了"，不如说...
```

## 二、持久化记忆

### 2.1 概念

持久化记忆是指将对话数据（会话、消息、摘要）存储在非易失性存储介质（MySQL 数据库）中，使得数据在服务重启、页面关闭后依然可用。本项目的记忆体系分为三层：

```
sessions 表（会话层）
  └── chat_messages 表（消息层）
       └── chat_summaries 表（摘要层）
```

### 2.2 作用

- **长期存储**：对话记录在服务重启后不丢失
- **历史回顾**：用户可随时查看、继续之前的任意会话
- **跨会话隔离**：不同会话之间的上下文互不干扰
- **会话管理**：支持创建、重命名、删除会话等完整 CRUD 操作

### 2.3 实现思路

#### 2.3.1 数据库表设计

**sessions 表**（会话元信息）：

```sql
CREATE TABLE IF NOT EXISTS sessions (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    user_id    INT NOT NULL,
    session_id VARCHAR(100) NOT NULL UNIQUE,
    chat_type  VARCHAR(20) NOT NULL COMMENT 'chain or agent',
    title      VARCHAR(200) DEFAULT '新对话',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id),
    INDEX idx_user_chat_type (user_id, chat_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

| 字段 | 说明 | 作用 |
| :--- | :--- | :--- |
| `user_id` | 用户 ID | 关联 users 表，隔离不同用户的数据 |
| `session_id` | 会话标识符 (UUID[:8]) | API 交互的唯一标识 |
| `chat_type` | "chain" 或 "agent" | 区分恋爱大师和超级智能体 |
| `title` | 会话标题 | 前端列表展示（默认为"新对话"） |
| `updated_at` | 自动更新时间戳 | 按最后活跃排序会话列表 |

**chat_messages 表**（消息详细记录）：

```sql
CREATE TABLE IF NOT EXISTS chat_messages (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    session_id VARCHAR(100) NOT NULL,
    role       VARCHAR(20) NOT NULL COMMENT 'user or assistant',
    content    TEXT NOT NULL,
    msg_order  INT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_session_id (session_id),
    INDEX idx_session_order (session_id, msg_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

| 字段 | 说明 | 作用 |
| :--- | :--- | :--- |
| `session_id` | 所属会话 | 关联 sessions 表 |
| `role` | "user" 或 "assistant" | 区分消息发送方 |
| `content` | 消息内容 | TEXT 类型，支持长文本 |
| `msg_order` | 消息序号 | 自增排序，保证消息顺序 |
| 复合索引 | (session_id, msg_order) | 加速按会话按序查询 |

**chat_summaries 表**（对话摘要）：

```sql
CREATE TABLE IF NOT EXISTS chat_summaries (
    id             INT AUTO_INCREMENT PRIMARY KEY,
    session_id     VARCHAR(100) NOT NULL UNIQUE,
    summary        TEXT,
    updated_at     DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_session_id (session_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

- `session_id` 设为 UNIQUE，每个会话只有一条摘要记录
- `summary` 字段存储 LLM 生成的浓缩文本

def create_session(user_id, chat_type, title=None):
    session_id = str(uuid.uuid4())[:8]
    if title is None:
        title = "新对话"
    conn = get_db()
    try:
        with conn.cursor() as cur:
            cur.execute(
                "INSERT INTO sessions (user_id, session_id, chat_type, title) VALUES (%s, %s, %s, %s)",

        conn.commit()

    return session_id

#### 2.3.3 消息 CRUD

**保存消息**：

```python
def save_message(session_id, role, content):
    # 自增 msg_order
    cur.execute(
        "SELECT COALESCE(MAX(msg_order), 0) + 1 AS next_order "
        "FROM chat_messages WHERE session_id=%s",
        (session_id,),
    )
    next_order = cur.fetchone()["next_order"]
    cur.execute(
        "INSERT INTO chat_messages (session_id, role, content, msg_order) VALUES (%s, %s, %s, %s)",
        (session_id, role, content, next_order),
    )
```

- 每次插入先查询当前最大 `msg_order` 再加 1，保证线程安全的消息顺序

**获取历史消息**：

```python
def get_session_messages(session_id):
    cur.execute(
        "SELECT role, content, msg_order, created_at FROM chat_messages "
        "WHERE session_id=%s ORDER BY msg_order ASC",
        (session_id,),
    )
```

- 按 `msg_order ASC` 升序排列，未读的旧消息在前，新消息在后

**加载最近消息**（用于构建上下文）：

```python
def load_recent_messages(session_id, limit=RECENT_LIMIT):  # RECENT_LIMIT = 50
    cur.execute(
        "SELECT role, content FROM chat_messages "
        "WHERE session_id=%s ORDER BY msg_order DESC LIMIT %s",
        (session_id, limit),
    )
    rows = cur.fetchall()
    rows = list(reversed(rows))  # 反转回时间正序
    return rows
```

- 使用 `ORDER BY DESC LIMIT N` 获取最新的 N 条消息
- 在 Python 中反转回时间正序，方便直接拼接上下文

## 三、对话摘要

### 3.1 概念

对话摘要（Dialogue Summarization）是指利用 LLM 自动将长对话压缩为精简摘要文本的机制。随着对话轮次增加，完整的历史消息会超出 LLM 的上下文窗口或造成 Token 浪费。摘要提供了一种"有损压缩"方案——丢弃对话细节，保留核心信息。

**核心思想：**

```
原始对话（N 条消息） → LLM 压缩 → 摘要（< 500 字）
                                        ↓
               摘要 + 最近 50 条消息 → 构建上下文 → 注入 LLM
```

### 3.2 作用

- **控制上下文窗口**：避免长对话耗尽 LLM 的 token 限制（DeepSeek 上下文窗口虽大，但长上下文增加延迟和成本）
- **保留核心信息**：用户的身份、兴趣、目标、关键问题和 AI 的建议被高效浓缩
- **增量更新**：不是每次对话都重新生成摘要，而是基于已有摘要增量追加新内容
- **Token 成本优化**：用摘要替代全部历史消息，大幅降低每次对话的输入 token 量

### 3.3 实现思路

#### 3.3.1 触发条件

摘要更新不是每条消息都触发，而是采用**双条件"或"策略**：

```python
# app/chat_history.py
SUMMARY_INTERVAL = 5          # 每 5 轮对话触发一次
SUMMARY_TOKEN_THRESHOLD = 4000  # 累计字符超过 4000 时强制触发

def update_summary(session_id):
    msg_count = get_message_count(session_id)

    # 条件 1：按固定轮次触发（每轮 = user + assistant 两条消息）
    rounds = msg_count // 2
    if rounds % SUMMARY_INTERVAL != 0:
        # 条件 2：按 token 阈值触发（粗略估计，中文字符约 2 字符/token）
        total_chars = get_total_chars(session_id)
        estimated_tokens = total_chars / 2
        if estimated_tokens < SUMMARY_TOKEN_THRESHOLD:
            return  # 两个条件都不满足，跳过摘要生成

    # ... 执行摘要生成 ...
```

| 条件 | 触发时机 | 作用 |
| :--- | :--- | :--- |
| **轮次触发** | 每 5 轮（10 条消息） | 保证摘要不会过时太久 |
| **Token 阈值触发** | 累计中文字符 > 8000（约 4000 token） | 消息突然暴增时强制压缩 |

两个条件满足**任意一个**即触发更新，否则跳过以减少不必要的 LLM 调用。

#### 3.3.2 增量更新策略

摘要不是从头开始重写，而是**基于已有摘要 + 新对话行**增量生成：

```python
def update_summary(session_id):
    # 1. 获取已有摘要
    existing = load_summary(session_id)

    # 2. 获取最近 20 条消息作为"新对话行"
    recent = load_recent_messages(session_id, 20)
    if len(recent) < 2:
        return

    # 3. 格式化新对话行
    new_lines = ""
    for msg in recent:
        prefix = "用户" if msg["role"] == "user" else "AI"
        new_lines += f"{prefix}: {msg['content']}\n"

    # 4. 调用 LLM 生成新摘要
    prompt = ChatPromptTemplate.from_messages([
        ("human", (
            "请将以下对话压缩为中文摘要，只保留以下信息：\n"
            "1. 用户的身份、兴趣、目标\n"
            "2. 用户提出的主要问题或请求\n"
            "3. AI给出的关键回答或建议\n"
            "不要重复对话细节，只做概括。\n\n"
            "当前摘要：\n{summary}\n\n"
            "新的对话行：\n{new_lines}\n\n"
            "新的摘要（不超过500字）："
        )),
    ])
    chain = prompt | llm | StrOutputParser()
    new_summary = chain.invoke({"summary": existing, "new_lines": new_lines}).strip()

    if new_summary:
        save_summary(session_id, new_summary)
```

**增量策略的优势：**

- 第 1-5 轮生成的摘要作为"当前摘要"
- 第 6-10 轮触发更新时，LLM 既能看到"当前摘要"又能看到"新的对话行"
- LLM 将新信息融入旧摘要，输出一份更完整的摘要
- 相比每次从头生成全部消息的摘要，token 消耗大幅降低

#### 3.3.3 Prompt 设计分析

摘要生成的 Prompt 包含三个关键设计：

```
1. 用户的身份、兴趣、目标        ← 长期信息，跨轮次保留
2. 用户提出的主要问题或请求      ← 短期信息，本轮关注点
3. AI给出的关键回答或建议       ← 决策信息，回答的要点

不要重复对话细节，只做概括。    ← 压缩指令，控制长度

当前摘要：{summary}             ← 上下文注入，已有摘要
新的对话行：{new_lines}         ← 上下文注入，新增消息

新的摘要（不超过500字）：        ← 长度约束
```

这个设计确保了摘要始终包含三个维度的信息：**"谁在问"、"问了什么"、"得到了什么答案"**。

#### 3.3.4 摘要存储

```python
def save_summary(session_id, summary_text):
    cur.execute(
        "INSERT INTO chat_summaries (session_id, summary) VALUES (%s, %s) "
        "ON DUPLICATE KEY UPDATE summary=%s",
        (session_id, summary_text, summary_text),
    )
```

- 使用 `ON DUPLICATE KEY UPDATE`：如果该会话已有摘要则更新，否则插入新记录
- 每个会话只有一条摘要记录，消息存储在 chat_messages 表

#### 3.3.5 摘要的消费

摘要被 `build_context()` 函数消费，与最近消息一起构成上下文：

```python
def build_context(session_id):
    summary = load_summary(session_id)
    recent = load_recent_messages(session_id, RECENT_LIMIT)  # 50条

    parts = []
    if summary:
        parts.append(f"【对话摘要】\n{summary}")

    if recent:
        lines = ["【最近对话】"]
        for msg in recent:
            prefix = "用户" if msg["role"] == "user" else "AI"
            lines.append(f"{prefix}: {msg['content']}")
        parts.append("\n".join(lines))

    return "\n\n".join(parts)
```

**上下文层次：**

```
【对话摘要】          ← 压缩后的长期记忆（前 N 轮的核心信息）
用户的身份、关键问题、AI的建议...

【最近对话】          ← 未压缩的短期记忆（最近 50 条消息）
用户: 你刚才说的方法能具体一点吗？
AI: 当然，比如...
```

### 3.4 实现效果

- **智能触发**：异步按需触发，不对每次对话造成额外延迟（LLM 调用发生在流输出之后）
- **增量压缩**：基于已有摘要追加新内容，减少 token 浪费
- **无状态摘要存储**：摘要独立于消息存储，可随时重建
- **上下文质量**：即使对话长达上百轮，上下文窗口始终包含摘要 + 最近 50 条消息，不会超出上下文限制

## 四、三者关系

### 4.1 完整数据流

```
用户输入消息
  │
  ├── 是否已有 session_id？
  │     ├── 否 → 新建会话（create_session）
  │     └── 是 → 继续
  │
  ├── build_context(session_id)
  │     ├── load_summary(session_id)        ← 读取持久化的摘要
  │     └── load_recent_messages(session_id) ← 读取最近 50 条消息
  │
  ├── save_message("user", message)         ← 持久化用户消息
  │
  ├── LLM 推理（基于摘要 + 历史 + 新消息）
  │
  ├── stream 输出（SSE 推送到前端）
  │
  ├── save_message("assistant", response)   ← 持久化 AI 回复
  │
  └── update_summary(session_id)            ← 判断是否触发摘要更新
        ├── 每 5 轮 → 触发
        ├── token > 4000 → 触发
        └── 否则 → 跳过
```

### 4.2 核心维度对比

| 维度 | 多轮对话 | 持久化记忆 | 对话摘要 |
| :--- | :--- | :--- | :--- |
| **本质** | 上下文传递机制 | 数据存储体系 | 信息压缩策略 |
| **存储媒介** | 运行时内存 + LLM 输入 | MySQL 数据库 | MySQL + LLM |
| **数据量** | 当前请求的上下文字符串 | 所有历史会话和消息 | 每条会话一条摘要 |
| **生命周期** | 单次请求期间 | 永久（直到用户删除） | 永久（随会话更新） |
| **更新频率** | 每次请求 | 每次保存 | 每 5 轮或 token 超阈值 |
| **核心功能** | 让 AI"记得"刚才说了什么 | 让数据"留下来"重启不丢 | 让上下文"不膨胀"控制成本 |

### 4.3 三者的协作定位

```
持久化记忆（MySQL）：底座存储
  ├── 提供原始消息给多轮对话
  ├── 提供摘要存储给摘要系统
  └── 提供会话列表给前端

多轮对话（session_id）：运行时机制
  ├── 读取持久化记忆构建上下文
  ├── 驱动 LLM 生成回复
  └── 消费对话摘要作为上下文的一部分

对话摘要（LLM 生成）：优化工具
  ├── 读取持久化记忆中的原始消息
  ├── 生成压缩版信息回写持久化记忆
  └── 被多轮对话消费以减少上下文长度
```

### 4.4 关键设计决策

1. **摘要为什么不替换消息？**：摘要是有损压缩，丢失细节。保留最近 50 条原始消息 + 摘要的组合，既保证了长距离信息的留存，又不丢失近距离的对话细节。

2. **为什么摘要不在前端生成？**：摘要需要理解整段对话的语义，这更适合由后端 LLM 完成。前端只负责展示和交互。

3. **为什么使用 MySQL 而非 Redis？**：对话数据需要持久化存储和复杂查询（按用户、按类型过滤、排序）。MySQL 的关系模型和索引更合适，Redis 可以作为未来缓存优化层的补充。

4. **`msg_order` 自增 vs UUID？**：自增整数序号保证了消息的顺序性，且对前端分页、后端断点续传更加友好。

## 五、总结

| 概念 | 一句话总结 |
| :--- | :--- |
| **多轮对话** | 通过 session_id 和 build_context 将历史对话传入 LLM，使 AI 具备"记忆力" |
| **持久化记忆** | 基于 MySQL 三层表结构，让所有对话数据在重启后依然可用 |
| **对话摘要** | 通过 LLM 自动压缩长对话，以增量更新策略控制上下文窗口不膨胀 |

三者构成完整的对话连续性保障体系：**持久化记忆负责"存得住"**，**多轮对话负责"记得起"**，**对话摘要负责"装得下"**。
