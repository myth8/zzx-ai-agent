# 阶段 0.4：从 Flask 开发服务器走向可验证的生产运行基线

“本地可以启动”不等于“具备生产运行条件”。开发服务器缺少进程管理、优雅退出、稳定并发模型和标准访问日志；如果没有 request_id、统一错误格式和自动化测试，线上故障也很难关联前端报错、Nginx 日志和 Flask 堆栈。

阶段 0.4 的目标是建立最小但完整的生产基线：

```text
Nginx 提供静态页面与反向代理
      │
      ▼
Gunicorn 管理 Flask 进程与线程
      │
      ▼
Flask 完成鉴权、限流和业务处理
  ├─→ MySQL 保存业务数据
  ├─→ Redis 保存认证与限流状态
  └─→ RAG 进程内索引提供检索

每次代码提交
      │
      ▼
GitHub Actions
  ├─→ 后端安全回归与编译检查
  ├─→ Gunicorn 配置校验
  ├─→ 前端安全测试与生产构建
  └─→ 依赖审计与密钥扫描
```

## 一、生产环境拒绝 Flask 开发服务器

开发环境仍然可以使用：

```bash
python run.py
```

但当 `APP_ENV=production` 时，`run.py` 会直接拒绝启动，并提示使用：

```bash
gunicorn -c gunicorn.conf.py wsgi:app
```

这样可以避免部署人员只设置了 production 配置，却仍然无意中运行 Flask 内置开发服务器。

新的 `wsgi.py` 只负责暴露应用对象：

```python
from app import create_app

app = create_app()
```

Gunicorn 通过 `wsgi:app` 导入它，应用仍然沿用现有 Factory、配置校验和数据库初始化流程。

## 二、为什么使用 gthread

当前 Gunicorn 默认参数：

| 参数 | 默认值 | 用途 |
|---|---:|---|
| Worker Class | `gthread` | 在线程中并发处理普通请求和 SSE |
| Workers | 1 | 保持唯一进程内 RAG 索引版本 |
| Threads | 4 | 允许多个请求或流式连接并发 |
| Timeout | 180 秒 | 覆盖 Agent 和模型调用时间 |
| Graceful Timeout | 30 秒 | 给退出中的请求保留收尾时间 |
| Keep-Alive | 5 秒 | 复用短期 HTTP 连接 |

选择一个 Worker 不是因为 Gunicorn 不能启动多个进程，而是因为当前 RAG 引擎仍持有进程本地状态：

- 当前文档切片列表。
- Chroma Vector Store 引用。
- BM25 Retriever。
- Reranker 模型。
- retired collection 与活跃查询计数。

如果立即设置多个 Worker：

```text
Worker A 收到重建请求并切换到索引 V2
Worker B 没有收到进程内状态更新，仍使用 V1
      │
      ▼
相同查询被负载均衡到不同 Worker
      │
      ▼
得到不同检索结果
```

因此当前使用“单进程、多线程”。Redis 限流已经可以跨 Worker 共享，但 RAG 状态还没有达到这个条件。

升级多 Worker 前需要：

1. 使用 Redis 分布式锁串行化索引变更。
2. 持久化 active index version。
3. 为所有进程发布索引切换通知。
4. 让查询显式绑定某个完整索引版本。
5. 验证旧 collection 的跨进程回收策略。

## 三、标准输出与 request_id 访问日志

Gunicorn 的 access log 和 error log 输出到标准输出，便于 Docker、Systemd 或日志平台统一收集。

访问日志包含响应头中的 `X-Request-ID` 和请求耗时：

```text
client method path status bytes request_id="..." duration_us=...
```

这样一次请求可以跨越：

```text
浏览器错误提示
      │
      ▼
Nginx 访问日志
      │
      ▼
Gunicorn 访问日志
      │
      ▼
Flask 应用日志与异常堆栈
```

## 四、request_id 中间件

请求进入 Flask 后，会检查客户端提供的 `X-Request-ID`。只有满足以下规则才会接受：

- 长度 8 到 128。
- 只包含字母、数字、点、下划线和横线。

不满足条件时生成新的 UUID：

```python
g.request_id = uuid.uuid4().hex
```

响应统一添加：

```http
X-Request-ID: 7f4d...
```

普通 JSON 错误、SSE error 事件、应用日志和 Gunicorn access log 都使用同一个 ID。

客户端可以提供合法 request_id，便于前端先生成追踪 ID；但严格格式限制可以避免攻击者向日志注入换行或超长内容。

## 五、统一错误响应

错误结构统一为：

```json
{
  "code": "STABLE_ERROR_CODE",
  "message": "用户可以理解的提示",
  "request_id": "...",
  "details": null
}
```

其中：

- `code` 供前端稳定判断，不依赖中文文案。
- `message` 只包含可以公开的信息。
- `request_id` 用于关联服务端日志。
- `details` 只放字段级公开信息，不能放异常堆栈、SQL 或密钥。

400、404、405、413、429 和未捕获异常都有统一处理。未捕获异常只在服务端记录完整堆栈，客户端固定收到 `INTERNAL_ERROR`。

SSE 已开始传输后不能再可靠改变 HTTP 状态码，因此流中使用稳定的 `event: error`，仍然包含相同 request_id。

## 六、日志脱敏

日志过滤覆盖常见形式：

- `Authorization: Bearer ...`。
- Cookie。
- API Key。
- JWT Secret。
- Password。
- Token。

过滤器先处理普通日志消息，Formatter 再对最终格式化文本执行一次脱敏，确保异常 traceback 中出现的敏感字符串也不会漏过。

日志格式为：

```text
时间 级别 logger request_id=... 消息
```

需要明确：正则脱敏是最后一道防线，不应主动把完整请求体、用户对话或密钥写入日志后再依赖正则补救。

## 七、CORS 与可信代理

CORS 不再使用无限制来源，而是读取精确白名单：

```ini
CORS_ORIGINS=https://frontend.example.com
```

只有请求 Origin 在白名单中时，才返回对应的 `Access-Control-Allow-Origin` 和凭据许可。

限流依赖客户端 IP，因此代理信任边界必须同步配置：

```ini
TRUST_PROXY_HOPS=0
```

默认值 0 表示不信任转发头。只有 Flask 直接位于一层可信 Nginx 后方时才设为 1。这个数字表示信任的代理层数，不是开关越大越好。

错误配置可能让客户端伪造 `X-Forwarded-For`，从而绕过注册和登录 IP 限制。

## 八、API 与页面安全响应头分工

Flask API 返回严格 CSP：

```text
default-src 'none'
frame-ancestors 'none'
base-uri 'none'
```

API 响应本身不需要加载脚本、样式或图片，因此可以采用最严格默认值。

真正加载 Vue 的 HTML 页面由 Nginx 设置页面 CSP，包括：

- 脚本只允许同源。
- 对象资源全部禁止。
- 页面禁止被其他站点嵌入。
- 表单只提交同源。
- API 连接只允许同源。
- 字体仅允许现有字体来源。

两处同时增加 `nosniff`、Referrer Policy、Frame Policy 和 Permissions Policy。不能只给 API 加 CSP，然后误以为前端页面已经受到保护。

## 九、CI 后端任务

GitHub Actions 后端任务使用 Python 3.11，并启动独立 Redis 7 服务：

```text
检出代码
      │
      ▼
安装 Python 3.11 与依赖缓存
      │
      ▼
等待 Redis 健康检查通过
      │
      ▼
运行 36 项后端回归测试
      │
      ▼
编译 app、tests 和启动配置
      │
      ▼
校验 Gunicorn worker 与线程参数
```

测试设置 `APP_ENV=test`，认证和限流都连接 Redis DB 15。这样限流测试确实操作 Redis，而不是因为 CI 中没有 Redis 就被跳过。

同时设置 Hugging Face 和 Transformers 离线模式，单元测试不会因为模型下载或外部网络波动而失败。需要模型的测试通过 Mock 验证初始化并发逻辑，不在 CI 中重复下载大型权重。

## 十二、当前边界与下一步

阶段 0.4 建立的是生产基线，不代表已经完成所有高可用工作。当前仍需继续推进：

1. 数据库连接池和清晰事务边界。
2. Alembic 或 Flask-Migrate 版本化迁移。
3. 多 Worker RAG 索引版本协调。
4. Redis 高可用、监控和容量告警。
5. Prometheus 指标、结构化日志和告警规则。
6. 真正的部署流水线、回滚与灰度策略。
7. 测试数据库和外部服务契约测试。

现阶段最重要的变化是：项目不再依赖“开发者记得正确操作”，而是通过启动拒绝、配置校验、稳定错误和 CI 自动阻止明显不安全的运行方式。
