# 开篇：从 AI 对话 Demo 到可演进的 Agent 平台

大多数 AI 应用的第一版都很相似：准备一个 Prompt，调用一次模型接口，然后把回答显示在页面上。

这种 Demo 能快速证明想法，却很难直接承载真正的产品需求。当项目开始增加用户登录、多轮对话、知识库、工具调用、流式输出和长期记忆后，问题会迅速从“模型能不能回答”变成：

- 用户数据是否安全？
- 一个请求失败或重复提交后，会不会产生重复消息？
- 多个用户同时对话时，服务是否还能稳定运行？
- SSE 连接断开后，任务能否继续并恢复？
- 对话越来越长时，应该保留哪些上下文？
- RAG 的答案来自哪里，能否追溯和更新？
- Agent 调用工具失败后，应该重试、降级还是停止？
- 多个 Agent 之间如何协作，又如何避免无限委派？

ZZX AI Agent 正处在这个转折点。

这个系列不会只记录“又增加了一个功能”，而是尝试完整呈现一个 AI 对话项目如何逐步补齐安全、数据、并发、记忆、检索、Agent 和工程化能力，最终成为一个可持续迭代的平台。

## 一、项目是什么

ZZX AI Agent 是一个前后端分离的智能体项目，目前提供两个 AI 交互入口，并为管理员提供独立的 RAG 知识库管理空间：

### AI 恋爱大师

面向情感沟通与关系分析，强调：

- 理解关系中的上下文和言外之意。
- 提供温和、清醒且具有边界感的建议。
- 通过多轮对话延续用户当前问题。
- 使用会话摘要保存较长对话的核心信息。

### AI 超级智能体

面向更通用的任务处理，强调：

- 分析和拆解用户目标。
- 使用 LangChain Agent 组织模型与工具。
- 通过 MCP 接入独立工具服务。
- 结合 RAG 检索项目知识。
- 以 SSE 方式流式返回任务进度和最终回答。

### RAG 知识库管理

面向管理员的知识运营入口，强调：

- 管理 Markdown 知识文档和结构化元数据。
- 查看实际切片、全部切片元信息以及 MySQL 与 Chroma 的映射关系。
- 上传或删除文档后安全刷新检索索引。
- 检查索引一致性，避免无意义的重复重建。
- 使用标题和主题元数据辅助 Chroma 与 BM25 一致过滤召回范围。

从产品视角看，它不是两个完全独立的聊天页面，而是同一个 Agent 平台上的两种能力形态：

```text
用户
 │
 ▼
ZZX AI Agent 平台
 ├─→ AI 恋爱大师垂直场景 ──→ 对话记忆
 ├─→ AI 超级智能体通用场景
 │       ├─→ 对话记忆
 │       ├─→ RAG 知识检索
 │       └─→ MCP 工具生态
 └─→ RAG 知识库管理 ──────→ RAG 知识检索
```

## 二、当前技术架构

项目当前主要由四部分组成：

```text
Vue 前端页面
      │
      ▼
Axios 与 SSE 请求
  ├─→ JWT 与权限 ──────────┬─→ MySQL
  │                         └─→ Redis
  ├─→ 会话与消息 ─────────────→ MySQL
  ├─→ Love Master Chain ──────→ 大模型服务
  └─→ Super Agent
          ├─→ 大模型服务
          ├─→ RAG 检索 ───────→ Chroma 与 BM25
          └─→ MCP 与本地工具 ─→ MCP Server
```

主要技术栈包括：

| 层次 | 当前技术 |
|---|---|
| 前端 | Vue 3、Vite、Vue Router、Axios、fetch SSE |
| 后端 | Python、Flask、PyMySQL |
| 模型与 Agent | LangChain、模型 API、Tool Calling |
| 数据库 | MySQL |
| 登录状态 | JWT、Redis |
| 知识检索 | Chroma、向量检索、BM25、Reranker |
| 工具协议 | MCP、FastMCP |
| 流式通信 | Server-Sent Events |

## 三、当前已经具备的能力

项目目前已经超过了最初的一问一答 Demo，具备以下基础能力：

### 用户与权限

- 用户注册、登录和密码哈希存储。
- 短期 Access Token 与 Refresh Token 自动续签。
- Redis 登录会话、单设备退出和全部设备退出。
- 普通用户与管理员角色。
- 管理员邀请码注册及登录后兑换。
- 会话资源按 `user_id + session_id` 进行归属校验。

### 对话与记忆

- 多会话管理。
- 用户消息和 AI 回复持久化。
- 最近消息上下文。
- 会话摘要。
- Love Master 与 Super Agent 独立会话类型。

### Agent 与工具

- LangChain Chain 与 Agent 两种运行方式。
- 本地工具调用。
- MCP 工具接入。
- RAG 检索。
- SSE 流式返回。

### 前端体验

- 登录、注册和智能体首页。
- 会话列表、创建、重命名和删除。
- 对话页面与流式内容展示。
- 管理员邀请码兑换入口。
- 统一视觉主题和响应式布局。
- Vite 同源代理，避免开发端口变化造成跨域问题。
- 管理员专属 RAG 文档、元数据和切片管理页面。
- Markdown 格式示例、上传进度和智能索引检查。

## 四、为什么还需要继续改造

“功能能够运行”和“系统可以长期可靠运行”之间仍然存在很大距离。

当前实现中的主要矛盾包括：

### 请求与任务仍然耦合

一次聊天请求需要同时承担：

```text
鉴权
  -> 保存用户消息
  -> 构建上下文
  -> 调用模型
  -> 调用 RAG 或 MCP
  -> 持续输出 SSE
  -> 保存最终回答
  -> 更新摘要
```

任何环节变慢，都会延长 Web 请求和线程占用。进程重启或连接中断时，也缺少一个独立的任务状态用于恢复。

### 数据一致性还不够强

- 重复点击或网络重试可能产生重复消息和重复模型调用。
- 消息顺序在并发写入时可能冲突。
- 会话删除依赖多条手工 SQL。
- 当前建表逻辑适合空数据库，但缺少正式的版本化迁移。

### 记忆仍是第一版

- 最近消息使用固定条数，而不是 Token 预算。
- 摘要没有明确记录覆盖到哪条消息。
- 摘要和原始消息可能重复进入上下文。
- 还没有用户可控的跨会话长期记忆。

### RAG 和 Agent 需要可靠性设计

- RAG 已完成单进程原子切换和失败回滚，但仍缺少增量更新与跨 Worker 版本协调。
- 中文 BM25 分词仍有优化空间。
- MCP 缺少统一超时、重试、熔断和生命周期管理。
- Agent 缺少明确的最大步骤、最大工具次数和总预算。

因此，后续改造不会简单地在 Flask 外层增加一个线程池，而是按照依赖关系逐步建立稳定的数据模型和任务模型。

## 五、优化原则

整个迭代计划遵循以下顺序：

```text
安全与权限
    │
    ▼
数据正确性与幂等
    │
    ▼
并发、任务与可靠 SSE
    │
    ▼
短期与长期记忆
    │
    ▼
RAG、MCP 与 Agent 可靠性
    │
    ▼
多 Agent 协作
    │
    ▼
测试、监控与部署
    │
    ▼
产品能力扩展
```

优先级背后的考虑是：

1. 先保证秘密、用户数据和权限边界安全。
2. 再保证请求不会重复、数据不会错乱。
3. 有了可靠任务状态后，再拆分 Worker 和流式事件。
4. 有了稳定消息模型后，再升级记忆与 RAG。
5. 单 Agent 运行可靠后，再增加多 Agent 协作。
6. 最后在统一底座上持续扩展产品功能。

如果顺序反过来，多 Agent、长期记忆和异步 Worker 都可能建立在不稳定的数据结构上，后续返工成本会更高。

## 六、阶段路线图

### 阶段 0：安全基线与配置治理

目标是消除最直接的安全风险。

主要内容：

- 敏感配置迁移到环境变量。
- Development、Test、Production 配置分层。
- 启动配置校验和日志脱敏。
- Git 密钥扫描。
- JWT、Redis 登录状态和资源归属。
- 管理员角色与权限装饰器。
- 输入、Markdown、工具和上传安全。
- 生产运行基线。

当前进度：

- 阶段 0.1“敏感配置治理”已完成代码改造。
- 阶段 0.2“认证与资源归属”已完成核心改造。
- 阶段 0.3“输入、工具与前端渲染安全”已完成：统一输入边界、AST 白名单、Markdown 双层清洗、Redis 差异化限流和稳定 SSE 错误已经落地。
- 阶段 0.4“生产运行基线”已完成基础项：Gunicorn、request_id、统一错误、精确 CORS、安全响应头和安全 CI 已落地。

### 阶段 1：数据库、事务、接口规范与幂等性

目标是解决重复请求和并发写入造成的数据问题。

计划包括：

- 引入 Flask-Migrate/Alembic。
- 使用版本化迁移替代启动时临时补字段。
- 增加数据库连接池和统一事务边界。
- 使用完整 UUID 或有序 ID。
- 增加 `client_message_id` 和 `Idempotency-Key`。
- 建立 `chat_runs` 和 `idempotency_records`。
- 修复消息顺序、会话更新时间和并发注册。
- 为会话和消息增加稳定分页。

完成后，相同请求的重试不会重复创建消息或再次调用模型。

### 阶段 2：并发处理、异步任务与可靠 SSE

目标是让 Web 请求不再承担完整的 AI 执行生命周期。

```text
Flask API
  ├─→ MySQL 消息与任务记录
  └─→ Redis 任务队列
              │
              ▼
          AI Worker
          ├─→ 模型、RAG、MCP
          ├─→ MySQL 消息与任务记录
          └─→ Redis Stream
                    │
                    ▼
               SSE Gateway
                    │
                    ▼
                   前端
```

计划包括：

- 短期使用 Gunicorn gthread 和有界并发。
- 中期引入 RQ、Dramatiq 或 Celery Worker。
- 建立 queued、running、succeeded、failed、cancelled、timed_out 状态。
- 增加超时、有限重试、心跳和任务恢复。
- SSE 增加事件 ID、心跳、断线续传和取消。
- 同一会话默认串行执行，避免回答顺序错乱。

### 阶段 3：短期记忆精细化与长期记忆 2.0

目标是让记忆可解释、可控制、可评测。

计划将记忆拆成四层：

```text
工作记忆和单次请求状态
          │
          ▼
短期记忆和当前会话消息
          │
          ▼
情景记忆和会话主题摘要
          │
          ▼
长期语义记忆和稳定偏好
```

主要内容：

- 按模型窗口计算动态 Token 预算。
- 建立摘要覆盖水位和增量摘要。
- 摘要任务异步执行。
- 抽取跨会话的稳定用户事实。
- 按相关性、重要性、可信度和时间衰减召回。
- 允许用户查看、修改、删除和关闭记忆。
- 默认谨慎处理身份、关系、健康等敏感信息。

### 阶段 4：RAG、MCP 与 Agent 可靠性

目标是把“可以调用”提升为“可以稳定运行和追踪”。

RAG 方向：

- 文档内容哈希和稳定 Chunk ID。
- 增量索引、索引版本和原子切换。
- 中文分词、向量与关键词混合检索。
- Rerank 并发控制。
- 引用来源、页码和版本追溯。
- 离线检索评测。

当前进度：管理员 RAG 管理闭环、文档与切片双表、完整切片元信息查看、稳定 Chunk ID、索引原子切换、失败回滚、一致性检查和双路元数据软过滤已经完成；增量索引、多 Worker 协调和离线评测仍待实施。

MCP 方向：

- 客户端连接和事件循环复用。
- 超时、重试、退避、熔断与降级。
- 工具输入输出 Schema 校验。
- 区分只读工具和高风险写入工具。
- 写操作使用 `action_id` 防止重复执行。

Agent 方向：

- 最大迭代次数、工具次数、时长和 Token 预算。
- 检测重复工具调用和无进展循环。
- 不向用户输出隐藏推理。
- 使用稳定的阶段状态和工具摘要。
- 根据任务类型选择普通 Chain、RAG 或 Agent。

### 阶段 4.5：多 Agent 协作与 A2A 演进

第一版多 Agent 不直接引入 A2A，而是优先完成内部任务图和统一 Agent Runtime。

```text
用户问题
   │
   ▼
任务路由
  ├─→ 简单任务：单 Agent
  │
  └─→ 复杂任务：协调 Agent
           ├─→ 专业 Agent A ─┐
           ├─→ 专业 Agent B ─┤
           └─→ 工具 Agent ───┤
                              ▼
                       评审与冲突检查
                              │
                              ▼
                       汇总唯一最终回答
```

核心任务包括：

- Agent 注册表和能力描述。
- 受控 DAG 任务图。
- 任务依赖、预算、取消和恢复。
- 防止循环依赖和无限委派。
- 评审 Agent 与最终汇总。
- 单 Agent 与多 Agent 的质量、成本和延迟对比。
- 预留 A2A 适配器，未来按需接入远程 Agent。

A2A 更适合独立服务、不同框架或跨组织 Agent 之间的发现与通信，不负责解决当前项目内部编排的核心问题，因此不在第一版强制引入。

### 阶段 5：前端交互、测试、可观测性与部署

目标是让系统能够定位问题、稳定发布和重复部署。

主要内容：

- 使用统一状态层管理用户、会话、消息和运行任务。
- 停止生成、失败重试、重新生成和任务恢复。
- 后端、前端和端到端自动化测试。
- Request ID、Trace ID 和 Run ID。
- API、模型、队列、数据库、SSE 和工具指标。
- `/livez`、`/readyz` 和内部详细健康检查。
- Docker Compose 编排 API、Worker、MySQL、Redis 和 MCP。
- CI 中执行测试、迁移验证、构建和安全扫描。

### 阶段 6：产品功能升级与业务扩展

在底层运行模型稳定后，继续扩展用户价值：

- 在现有管理员 RAG 管理基础上扩展用户知识库、文档版本和审计能力。
- Agent、模型、Skill 和工具中心。
- 对话搜索、标签、置顶、归档、导出和只读分享。
- 用户反馈和离线评测闭环。
- 模型路由、配额和成本控制。
- 图片、语音和文件等多模态能力。
- 多租户、审计和数据导出删除。
- 模板与定时 Agent 任务。

新产品功能必须复用统一的鉴权、资源归属、幂等、任务状态、审计和成本控制能力，避免重新形成无法追踪的独立调用链。

## 七、目标运行架构

经过主要阶段改造后，目标架构将从“请求内完成所有工作”演进为“API、任务和事件分离”：

```text
Vue Web
   │ 请求
   ▼
API 与 SSE 网关
  ├─→ JWT 与 Redis 登录状态 ──→ MySQL
  ├─→ MySQL
  └─→ Redis 任务队列
              │
              ▼
          AI Workers
          ├─→ Memory Service
          ├─→ RAG Service
          ├─→ MCP Tool Runtime
          ├─→ Model Gateway
          ├─→ MySQL
          └─→ Redis Stream
                    │ 事件
                    ▼
              API 与 SSE 网关
                    │ 响应
                    ▼
                 Vue Web
```

这套架构的核心不是“组件越多越好”，而是明确每一层的职责：

- API 负责鉴权、校验、幂等和创建任务。
- Worker 负责模型、RAG、工具和记忆处理。
- MySQL 保存业务事实和任务最终状态。
- Redis 承担登录状态、任务队列和实时事件。
- SSE Gateway 只负责向前端推送可恢复事件。
- 前端根据 `run_id` 展示状态，而不是绑定某一条长请求。

## 八、如何判断每个阶段是否真的完成

这个系列不会把“代码写完”直接视为完成。每个阶段至少需要回答五个问题：

1. 解决了什么具体风险或用户问题？
2. 数据结构和接口契约是否清晰？
3. 异常、并发和重复请求时会发生什么？
4. 是否有自动化测试或可重复的验证步骤？
5. 部署和旧数据升级是否有明确方案？

阶段成果通常包括：

- 设计结论。
- 关键代码改造。
- 配置或数据迁移说明。
- 测试与验证结果。
- 已知边界和下一阶段计划。

## 十、项目希望最终回答的问题

这次迭代的最终目标并不只是做出一个功能更多的聊天页面，而是尝试回答：

> 一个个人 AI Agent 项目，应该如何从 Demo 开始，在不过度设计的前提下，逐步获得真正可用的安全性、可靠性、记忆能力、工具能力和扩展能力？

因此，项目会保持两个原则：

第一，不为了架构而架构。每个新组件都必须对应已经出现或即将出现的实际问题。

第二，不用“能跑”替代“完成”。关键能力需要明确状态、错误边界、测试、监控和回滚方式。

## 结语

AI 应用最吸引人的部分往往是模型、Prompt 和 Agent，但真正决定它能否长期运行的，通常是那些不那么显眼的工程能力：权限、事务、幂等、任务状态、超时、记忆边界、日志和部署。

ZZX AI Agent 的后续迭代会沿着这条路线继续推进：先把基础打稳，再让 Agent 变得更聪明；先保证每次运行可控、可追踪，再让多个 Agent 参与协作。

这既是一个项目的开发记录，也是一份从 AI Demo 走向工程化 Agent 平台的实践笔记。
