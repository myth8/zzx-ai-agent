# 项目优化与迭代计划

## 1. 目标与原则

本计划基于当前前后端、数据库、RAG、MCP 与对话记忆实现整理。整体目标是先解决安全性和数据一致性问题，再提升并发能力、记忆质量与 Agent 可靠性，最后补齐工程化能力和产品功能。

建议按以下优先级推进：

1. 安全与数据正确性
2. 幂等性与任务运行模型
3. 并发处理与流式通信
4. 短期记忆和长期记忆
5. RAG、MCP 与 Agent 稳定性
6. 测试、监控、部署与产品扩展

不建议一开始只在 Flask 接口外层增加线程池。当前 Flask 已使用多线程模式，而 SSE 和 Agent 调用属于长耗时任务，简单叠加线程池容易造成线程长期占用、数据库连接增长和任务状态丢失。线程池可以作为短期过渡方案，长期应将请求接入、任务执行和事件推送拆开。

## 2. 当前主要问题

### 2.1 安全与权限

- 配置文件中存在数据库密码、JWT 密钥、模型 API Key 等敏感配置，MCP 服务中也存在第三方 API Key。
- 部分聊天 SSE 接口没有统一登录校验。
- 会话列表按用户查询，但重命名、删除、消息查询等操作主要依赖 session_id，缺少完整的资源归属校验。
- 生产启动方式仍包含 debug 配置。
- CORS、请求体大小、接口频率、上传文件类型和输入长度缺少统一限制。
- 计算工具使用 eval，存在表达式注入风险。
- 前端 Markdown 渲染和链接处理需要增加内容清洗与安全协议限制。

### 2.2 数据库与一致性

- 会话 ID 截取 UUID 前 8 位，长期使用存在碰撞风险。
- 消息顺序通过查询 MAX(msg_order) 再加一生成，并发写入时可能出现重复序号。
- 写入消息后没有可靠更新会话 updated_at，导致最近会话排序可能不准确。
- 删除会话依赖多条手工 SQL，缺少外键级联和事务保护。
- 数据库方法频繁创建新连接，缺少连接池。
- 注册流程先查询再插入，并发情况下仍可能触发重复写入异常。
- 项目缺少正式的数据库迁移和版本管理机制。

### 2.3 请求幂等性

- 用户消息在 SSE 开始前保存，浏览器重试、网络重连或重复点击会产生重复消息和重复模型调用。
- AI 回复通常在流结束后才保存，断开连接或服务异常时容易形成只有用户消息、没有明确任务状态的记录。
- 当前没有独立的运行记录，无法可靠表达排队、执行中、成功、失败、取消和超时。
- 重试时无法判断是返回上一次结果，还是重新发起一次模型调用。

### 2.4 并发与 SSE

- 长时间 SSE 请求会持续占用 Web 工作线程。
- 请求执行、Agent 推理、工具调用和事件输出耦合在一个进程中，进程重启后任务状态难以恢复。
- SSE 通过 GET 查询参数传递完整问题，会进入浏览器历史、代理日志和访问日志。
- 原生 EventSource 不方便添加 Authorization 请求头，这也是聊天接口认证设计需要调整的原因之一。
- SSE 缺少稳定的事件 ID、断线续传、心跳、取消和明确的错误事件。
- 原始异常直接返回客户端可能泄露内部信息。

### 2.5 对话记忆

当前实现具备最近消息和对话摘要，但仍偏简单：

- 最近消息采用固定条数，不能适应不同模型上下文窗口和不同消息长度。
- Token 估算较粗，中文场景误差较大。
- 摘要触发条件达到总长度阈值后，可能在后续对话中频繁重复触发。
- 每次重复摘要最近一批消息，缺少“摘要已经覆盖到哪条消息”的水位记录。
- 构建上下文时同时加入摘要和较多历史原文，容易重复消耗 Token。
- 摘要生成与主请求同步执行，会拉长 SSE 请求占用时间。
- 尚未形成跨会话的用户偏好、目标、约束和重要事实等长期记忆。
- 缺少让用户查看、修改、删除或关闭记忆的能力。

### 2.6 RAG、MCP 与 Agent

- RAG 首次查询时可能同步初始化或重建索引，影响首请求延迟。
- 文档索引缺少内容哈希、增量更新、版本和稳定分块 ID。
- BM25 直接按空格切分对中文效果有限。
- 检索结果需要补充稳定来源、引用和可追溯信息。
- 重排模型需要考虑并发加载保护和独立资源隔离。
- MCP 初始化状态缺少并发锁，异步调用和事件循环的生命周期较分散。
- MCP 缺少统一超时、重试、退避、熔断、健康检查和降级策略。
- Agent 流式输出原始思考内容不适合作为正式产品能力，应改成可控的阶段状态和工具调用摘要。

### 2.7 前端功能与工程化

- 前端视觉已经完成一轮优化，下一步重点应转向交互状态和稳定性。
- 需要统一处理登录失效、请求错误、流式重连、取消生成、重新生成和失败重试。
- 会话及消息较多时需要分页、增量加载或虚拟列表。
- API 地址应使用环境配置，避免写死。
- Nginx 上游地址需要按实际部署环境统一配置。
- 当前缺少完整的自动化测试、持续集成、运行指标和健康检查。

## 3. 推荐目标架构

### 3.1 请求和任务模型

推荐将一次聊天拆成两步：

~~~text
前端提交消息
  -> API 校验用户、会话和幂等键
  -> 创建用户消息与 chat_run
  -> 任务进入队列
  -> Worker 执行模型、RAG 和工具调用
  -> 事件写入事件流
  -> SSE 网关推送进度
  -> 最终回复和运行状态写入 MySQL
~~~

短期可以使用 Gunicorn 的 gthread worker、数据库连接池和并发限制改善承载能力。中期建议引入 Redis 队列与独立 AI Worker，使 Web 服务只负责鉴权、参数校验、创建任务和流式转发。

### 3.2 推荐接口

- POST /api/sessions/{session_id}/messages
  - 请求头携带 Idempotency-Key。
  - 请求体携带 client_message_id 和消息内容。
  - 返回 message_id、run_id 和 status。
- GET /api/runs/{run_id}
  - 查询任务状态和最终结果。
- GET /api/runs/{run_id}/events
  - 订阅 SSE 事件，支持事件 ID、心跳和断线续传。
- POST /api/runs/{run_id}/cancel
  - 取消仍在排队或执行中的任务。

同一个用户使用相同幂等键和相同请求内容时，返回原任务；相同幂等键对应不同请求内容时返回 409，防止误复用。

### 3.3 推荐数据表

chat_runs 用于记录任务状态：

- id、user_id、session_id、user_message_id、assistant_message_id
- status：queued、running、succeeded、failed、cancelled、timed_out
- error_code、error_message、started_at、finished_at
- model、token_usage、cost、request_id

idempotency_records 用于记录接口幂等结果：

- user_id、endpoint、idempotency_key、request_hash
- response_status、response_body、resource_id、expires_at
- 唯一约束为 user_id、endpoint、idempotency_key

chat_messages 建议增加：

- 完整 UUID 或有序 UUID 主键
- client_message_id
- token_count
- status
- 唯一约束 session_id、client_message_id
- 通过事务、数据库序列或会话级锁生成稳定的消息顺序

## 4. 记忆系统 2.0

### 4.1 四层记忆

1. 工作记忆：当前一次请求中的问题、规划、工具结果和临时状态。
2. 短期记忆：当前会话中尚未被摘要覆盖的最近原始消息。
3. 情景记忆：按会话或主题生成的结构化摘要，保留事件、决定、未完成事项和时间范围。
4. 长期语义记忆：跨会话保存稳定的用户偏好、目标、约束和重要事实。

技能说明、系统规则和工具使用知识属于程序性知识，建议与用户记忆分开管理。

### 4.2 动态上下文预算

不再固定读取最近 50 条，而是按模型上下文窗口分配预算：

~~~text
可用上下文
= 模型窗口
- 系统提示词
- 工具定义
- 输出预留
- RAG 预留
- 安全余量
~~~

上下文推荐按以下顺序组装：

1. 系统提示词与安全规则
2. 与当前问题相关的长期记忆
3. 当前会话摘要
4. 摘要水位之后的未摘要消息
5. 最近若干轮原文
6. 当前用户消息

### 4.3 增量摘要

会话摘要需要记录：

- covered_through_message_id
- summary_version
- token_count
- model_name
- status
- created_at 和 updated_at

只有摘要水位之后新增的消息达到 Token 或轮数阈值时才触发增量摘要。摘要任务放到后台执行，主回答完成后不必等待摘要生成。上下文只加入摘要未覆盖的消息，避免摘要与原文重复。

### 4.4 长期记忆

建议建立 memory_items：

- user_id
- kind：profile、preference、goal、event、constraint
- content
- source_session_id、source_message_id
- importance、confidence、sensitivity
- status、expires_at、last_accessed_at

处理流程：

~~~text
候选事实抽取
  -> 敏感性和可信度判断
  -> 去重、合并或冲突标记
  -> 保存
  -> 按相关性、重要性和时间衰减召回
~~~

长期记忆应提供用户可见的管理页，支持不记忆、查看、编辑、删除和整体关闭。涉及关系、身份、健康等敏感信息时，默认不永久保存，或明确要求用户确认。

### 阶段 1：数据库、事务、接口规范与幂等性，预计 1 周

#### 阶段目标

解决并发下重复消息、顺序冲突、会话时间不更新和请求重复执行问题，并建立后续异步任务所需的数据模型。

#### 1.1 数据库迁移与约束

主要涉及：

- zzx-ai-agent-backend/app/chat_history.py
- zzx-ai-agent-backend/app/auth.py
- 新增 migrations 目录

具体任务：

1. 引入 Alembic 或 Flask-Migrate，不再通过手工修改数据库结构维护版本。
2. 为用户、会话、消息建立明确外键和删除策略。
3. session_id 和 message_id 改用完整 UUID、UUIDv7 或 ULID，不再截取前 8 位。
4. 为高频查询建立索引：
   - sessions：user_id、updated_at
   - messages：session_id、msg_order
   - runs：user_id、session_id、status、created_at
5. 为用户名或邮箱建立数据库唯一约束，以数据库作为并发注册的最终裁决者。
6. 删除会话使用事务与外键级联，避免部分表删除成功、部分失败。
7. 编写数据迁移脚本兼容已有短 ID 和已有消息记录，迁移前先生成备份与校验报告。

#### 1.2 消息顺序与事务

当前 MAX(msg_order) 加一在并发请求中不安全。推荐优先采用以下方案之一：

方案 A，推荐用于当前 MySQL 项目：

1. chat_sessions 增加 next_message_order。
2. 写消息事务中锁定对应会话行。
3. 读取并递增 next_message_order。
4. 插入消息并更新 sessions.updated_at。
5. 整个过程一次提交，任何步骤失败则全部回滚。

方案 B：

- 使用可排序的全局 ID 作为时间顺序，并保留 created_at 与唯一序号；适用于未来分布式写入，但改造范围更大。

无论采用哪种方案，都应增加 session_id、msg_order 唯一约束作为最后保护。

#### 1.3 数据库连接池和访问层

具体任务：

1. 用连接池替代每个辅助方法都创建新 PyMySQL 连接。
2. 统一 connection 和 transaction 上下文，确保异常自动回滚、连接自动归还。
3. 设置连接建立、查询、空闲连接和事务超时。
4. 将 SQL 访问集中到 repository 或 DAO 层，路由不直接拼接 SQL。
5. 对死锁和瞬时连接错误仅进行有限重试，重试写操作前必须先确认幂等性。
6. 记录慢查询并定期检查索引命中情况。

#### 1.4 聊天运行记录

新增 chat_runs 表，用来表达一次 AI 请求的完整生命周期。建议字段：

- id、user_id、session_id
- user_message_id、assistant_message_id
- status：queued、running、succeeded、failed、cancelled、timed_out
- model、agent_type、request_id
- error_code、error_message
- prompt_tokens、completion_tokens、total_tokens、estimated_cost
- retry_count、created_at、started_at、finished_at、updated_at

状态转换需要受控：

~~~text
queued -> running -> succeeded
                 -> failed
                 -> timed_out
queued/running   -> cancelled
~~~

禁止 succeeded 再回到 running。更新状态时使用条件更新或 version 字段，避免多个 Worker 同时完成同一个任务。

#### 1.5 幂等记录与规则

新增 idempotency_records，建议字段：

- user_id、endpoint、idempotency_key
- request_hash
- resource_type、resource_id
- response_status、response_body
- status：processing、completed、failed
- locked_until、expires_at、created_at、updated_at

唯一约束：

- user_id、endpoint、idempotency_key
- session_id、client_message_id

处理流程：

~~~text
收到请求
  -> 规范化请求并计算 request_hash
  -> 尝试插入幂等记录
  -> 插入成功：创建消息和 run
  -> 已存在且 hash 相同：返回原 run
  -> 已存在但 hash 不同：返回 409
~~~

幂等边界：

- 发送消息：必须使用 Idempotency-Key 和 client_message_id。
- 创建会话：可使用客户端生成的 client_session_id。
- 重命名：PUT 设置最终状态，本身应保持幂等，并可增加 version 防止覆盖新修改。
- 删除：重复删除返回 204，结果保持一致。
- 注册：依赖用户名或邮箱唯一索引，重复时稳定返回 409。
- MCP 写操作：后续使用 action_id，避免 Agent 重试时重复执行外部操作。

#### 1.6 接口规范调整

将“提交消息”和“接收流”解耦：

1. POST /api/sessions/{session_id}/messages 创建消息和运行任务。
2. GET /api/runs/{run_id} 查询状态。
3. GET /api/runs/{run_id}/events 订阅事件。
4. POST /api/runs/{run_id}/cancel 请求取消。

用户问题只放 POST 请求体，不再放入 SSE GET 查询参数。EventSource 的鉴权可以选择：

- 使用安全、SameSite 合理的 HttpOnly Cookie。
- 或先通过已鉴权 POST 换取短期、单次使用的 stream_token，再建立 SSE。
- 或前端使用 fetch 读取 ReadableStream，从而继续携带 Authorization 请求头。

#### 1.7 分页与响应格式

1. 会话列表使用 updated_at 与 id 组成游标。
2. 消息列表使用 msg_order 或可排序 ID 组成游标。
3. 限制单页最大条数，响应返回 next_cursor 和 has_more。
4. 时间统一以 UTC 存储，API 返回带时区的 ISO 8601。
5. 所有创建接口返回稳定资源 ID，不让前端依赖标题或数组位置识别对象。

#### 测试重点

- 20 个相同幂等键并发提交，只产生一条用户消息和一个 chat_run。
- 相同幂等键配不同内容稳定返回 409。
- 不同消息并发写入时 msg_order 唯一且连续或严格可排序。
- 中途抛出异常时，消息、会话时间、run 和幂等记录不会部分提交。
- 两个并发注册请求只创建一个用户，另一个返回明确冲突。
- 数据迁移在空库、现有数据副本和重复执行场景下均可验证。

#### 阶段交付物

- 可升级和可回滚的数据库迁移。
- 数据库连接池与统一事务访问层。
- chat_runs、idempotency_records 及相关索引。
- 新版消息提交、任务查询、事件订阅和取消接口。
- 接口契约文档与并发测试。

#### 验收标准

- 重复点击、超时重试和浏览器重连不会重复创建消息或调用模型。
- 并发写入下消息顺序稳定，会话最近更新时间正确。
- 任意 AI 请求都能通过 run_id 查询到明确状态。
- 会话和消息接口支持稳定分页。

### 阶段 2：并发处理、异步任务与可靠 SSE，预计 1 至 2 周

#### 阶段目标

让 Web 服务不再承担完整的模型推理生命周期，使长耗时请求可排队、可恢复、可取消、可观察，并能承受可预期的并发量。

#### 2.1 短期并发改造

短期方案用于异步架构完成前：

1. 使用 Gunicorn gthread worker 替换 Flask 开发服务器。
2. 根据 CPU、内存、数据库连接上限测算 worker 数和每个 worker 的线程数。
3. 设置每个模型调用、RAG、MCP 工具和整个请求的超时。
4. 使用有界线程池执行确实适合并发的 I/O 子任务，禁止使用无限队列。
5. 为每用户、每会话和全局模型请求设置并发上限。
6. 同一会话的消息默认串行执行，避免回答顺序和记忆状态交叉。

线程池只适合过渡和受控的 I/O 并发，不应用来包裹所有 Flask 请求。模型生成、SSE 连接和后台摘要都进入同一个线程池会产生相互饥饿。

#### 2.2 中期任务架构

推荐引入 Redis 和独立 Worker：

~~~text
Flask API
  -> MySQL 创建消息与 chat_run
  -> Redis 任务队列
  -> AI Worker
       -> 模型
       -> RAG
       -> MCP 和工具
       -> MySQL 保存最终结果
       -> Redis Stream 写运行事件
  -> SSE Gateway 读取事件并推送
~~~

可选实现：

- 轻量方案：RQ 或 Dramatiq。
- 功能完整方案：Celery。
- 如果不希望立即增加框架，可先实现数据库任务表加专用 Worker，但需要自行处理锁、重试和心跳。

#### 2.3 Worker 任务可靠性

具体任务：

1. Worker 领取任务时通过条件更新将 queued 改为 running。
2. 记录 worker_id、heartbeat_at 和 locked_until。
3. Worker 周期更新心跳；超时任务由恢复器重新排队或标记失败。
4. 自动重试只用于网络超时、限流等可恢复错误。
5. 参数错误、权限错误和安全拒绝不自动重试。
6. 每次重试继续使用同一 run_id 和幂等上下文。
7. 限制最大重试次数，并采用指数退避与随机抖动。
8. Worker 收到取消标记后，在模型块、工具调用和阶段边界主动终止。
9. 回复采用草稿或事件流存储，最终完成时再原子标记 assistant 消息为 completed。

#### 2.4 SSE 事件协议

统一事件类型：

- run.started
- assistant.delta
- tool.started
- tool.completed
- tool.failed
- run.heartbeat
- run.completed
- run.failed
- run.cancelled

每个事件包含：

- id：单调递增事件序号
- run_id
- type
- timestamp
- data

具体任务：

1. 每 15 至 30 秒发送心跳，避免代理关闭空闲连接。
2. 支持 Last-Event-ID，从 Redis Stream 或持久化事件中补发断线期间的数据。
3. 设置 Nginx 禁用 SSE 响应缓冲，并延长只针对流接口的读取超时。
4. 客户端断开不等于取消任务；只有显式调用 cancel 才取消。
5. 任务结束必须发送一种终态事件，不能既发送 error 又统一伪装成 DONE。
6. 面向用户的错误信息与内部异常分离。
7. 事件保留设置 TTL，最终消息和运行状态长期保存到 MySQL。

#### 2.5 背压与资源隔离

1. 队列达到阈值时返回 429 或 503，并给出 Retry-After。
2. 为普通聊天、Agent、摘要、索引构建划分不同队列，防止大任务阻塞在线聊天。
3. Reranker 等 CPU 密集型模型放入独立进程或独立模型服务。
4. 工具调用设置独立并发信号量，防止第三方服务雪崩。
5. 数据库连接池大小应小于数据库连接上限，并为迁移、管理任务保留连接。
6. 定义单个用户的并发 run、每分钟 Token 和每日成本上限。

#### 2.6 前端配套

1. 发送后立即创建 pending 消息，根据 run_id 更新状态。
2. 区分排队中、生成中、工具执行中、已完成、失败和已取消。
3. 页面刷新后通过 run_id 恢复状态并继续订阅。
4. 提供停止生成、失败重试和重新生成。
5. 网络断开时按退避策略重连，并从最后事件 ID 继续。
6. 重试提交必须复用原幂等键；用户主动重新生成则创建新的 run。

#### 测试与压测

- 逐步执行 10、50、100 个并发 SSE 连接，记录 P50、P95、P99 延迟与首 Token 时间。
- 验证数据库连接池、线程数、队列长度和内存没有持续增长。
- 模拟 Worker 强制退出、Redis 短暂中断、模型超时和 MCP 超时。
- 验证断线重连不丢事件、不重复拼接文本。
- 验证取消发生在模型生成和工具调用期间时都能进入 cancelled。
- 验证同一会话的两个请求不会以相反顺序写入最终上下文。

#### 阶段交付物

- 生产 WSGI 配置和容量参数说明。
- Redis、Worker、事件流和任务恢复器。
- SSE 事件协议文档。
- 前端运行状态、取消、恢复和重试交互。
- 并发压测脚本与基线报告。

#### 验收标准

- 100 个并发 SSE 连接不会耗尽数据库连接或导致健康检查失效。
- 页面刷新、短暂断网后可以恢复同一任务的流。
- Worker 异常后任务可以恢复、有限重试或明确失败，不会永久停在 running。
- 所有任务最终都进入 succeeded、failed、cancelled 或 timed_out。

### 阶段 3：短期记忆精细化与长期记忆 2.0，预计 1 至 2 周

#### 阶段目标

在明确 Token 预算内保留最近对话细节，通过增量摘要压缩历史，并在用户可控和可追溯的前提下实现跨会话长期记忆。

#### 3.1 先建立记忆评测基线

在改造代码前准备 30 至 50 组小型测试会话，覆盖：

- 用户姓名、偏好、禁忌和长期目标。
- 当前会话中的临时变量和指代关系。
- 用户后续修改偏好或明确否定旧信息。
- 无关旧记忆不应被召回。
- 敏感信息不应自动长期保存。
- 长对话达到摘要阈值后的事实保留。

每组定义预期召回内容、不应召回内容和最终回答要点，作为后续方案比较依据。

#### 3.2 Token 预算器

具体任务：

1. 使用目标模型对应 tokenizer；没有精确 tokenizer 时使用经过中文样本校准的估算器。
2. 为不同模型登记 context_window 和 max_output_tokens。
3. 在请求开始时扣除系统提示词、工具 schema、输出预留、RAG 预留和安全余量。
4. 剩余预算再分给长期记忆、会话摘要和最近原文。
5. 每个组成部分记录实际 Token，方便分析裁剪原因。
6. 超预算时优先裁剪低相关长期记忆与较旧原文，不能直接截断当前用户问题。

建议初始比例，可根据评测调整：

- 系统和工具：固定实际占用。
- 输出预留：总窗口的 15% 至 25%。
- RAG：可用输入预算的 25%。
- 长期记忆：可用输入预算的 10%。
- 会话摘要：可用输入预算的 20%。
- 最近原文：使用剩余预算。

#### 3.3 短期记忆与上下文选择

1. 不再固定读取最近 50 条。
2. 先读取摘要水位之后的消息，再从新到旧按 Token 装箱。
3. 至少保留最近一轮完整用户和助手消息，避免只保留半轮。
4. 工具原始输出只在当前 run 使用；进入历史前压缩为工具名、关键参数和结果摘要。
5. 对特别长的单条消息先保留开头、结尾和结构化摘要，并保留原文引用 ID。
6. 上下文构建器返回调试元数据：选中了哪些消息、记忆和文档、各自 Token 数及裁剪原因。

#### 3.4 增量会话摘要

新增或改造 session_summaries，字段建议：

- id、session_id
- summary_text 或结构化 summary_json
- covered_from_message_id
- covered_through_message_id
- source_message_count
- summary_version、prompt_version、model_name
- token_count、status
- created_at、updated_at

摘要触发规则：

1. 只统计 covered_through_message_id 之后的新消息。
2. 新增消息超过设定轮数或 Token 阈值时创建摘要任务。
3. 一次只允许同一会话存在一个 running 摘要任务。
4. 将旧摘要与新增原文合并为新摘要，不再反复总结相同的最近 20 条。
5. 摘要成功后原子推进覆盖水位；失败不推进，可稍后重试。
6. 摘要放入低优先级后台队列，不阻塞当前回答。

结构化摘要建议包含：

- 用户目标
- 已知事实
- 用户偏好与限制
- 已作决定
- 已尝试方案和结果
- 未完成事项
- 最近话题状态

#### 3.5 长期记忆抽取

长期记忆不应等于“把所有聊天都做向量化”。建议只保存具有未来价值的稳定信息：

- profile：稳定身份或背景。
- preference：表达风格、工具、技术栈等偏好。
- goal：持续目标和项目方向。
- constraint：预算、时间、禁止项等限制。
- event：对未来确实重要且有时效的事件。

抽取流程：

1. 回合结束后异步生成候选记忆。
2. 规则与模型共同判断是否值得保存。
3. 标注 importance、confidence、sensitivity 和 expires_at。
4. 使用规范化文本和向量相似度查找已有记忆。
5. 相同事实合并并增加证据来源。
6. 新旧事实冲突时保留版本与状态，不直接无痕覆盖。
7. 保存 source_session_id 和 source_message_id，保证可追溯。

默认不保存：

- 一次性问题和短期任务细节。
- 未经用户确认的高敏感推断。
- 密码、令牌、银行卡等秘密。
- 模型根据语气猜测出的身份、健康或关系结论。

#### 3.6 长期记忆召回

召回分两步：

1. 候选召回：按 user_id、状态、类型、过期时间过滤，再做关键词或向量检索。
2. 重排：综合相关性、重要性、可信度、最近访问时间和时间衰减。

建议评分：

~~~text
score
= relevance * 0.55
+ importance * 0.20
+ confidence * 0.15
+ recency * 0.10
~~~

实际权重通过评测调整。召回结果数量和总 Token 都要设上限。只有和当前问题真正相关的记忆才进入提示词，并以“可能相关的用户记忆”而不是绝对事实的方式提供给模型。

#### 3.7 用户控制与隐私

前端增加记忆管理页：

- 查看系统记住的内容、类型、来源和更新时间。
- 编辑错误记忆。
- 删除单条或清空全部记忆。
- 将记忆设为暂不使用。
- 关闭长期记忆。
- 当前消息提供“不要记住这条”。

后端保证删除后：

1. 数据库记录进入删除状态或物理删除。
2. 向量索引同步移除。
3. 缓存失效。
4. 后续上下文不再召回。
5. 审计日志只保留操作事实，不继续保留被删除内容。

#### 3.8 与 RAG 的边界

- 用户记忆回答“这个用户是谁、偏好什么、正在做什么”。
- RAG 回答“项目文档或知识库里有什么事实”。
- 会话摘要回答“当前会话之前讨论到了哪里”。

三个来源在上下文中使用不同标签，并在调试信息中分别统计，避免把文档内容错误写成用户记忆。

#### 测试重点

- 10 万 Token 等效长会话中，上下文始终不超过预算。
- 摘要水位推进后，已覆盖原文不再重复注入。
- 长度阈值达到后不会每轮重复摘要。
- 用户修改偏好后优先召回新版本，并能说明来源。
- 无关记忆和已删除记忆不进入上下文。
- 摘要 Worker 失败不影响主回答完成。
- 敏感信息抽取测试默认拒绝保存。

#### 阶段交付物

- Token 预算器和上下文构建器。
- 增量摘要表、任务和覆盖水位。
- memory_items、记忆抽取和召回服务。
- 记忆管理前端页面。
- 记忆评测数据集与对比报告。

#### 验收标准

- 上下文预算可解释且不会超限。
- 已摘要内容不再大量重复，摘要不会每轮触发。
- 新会话能召回真正相关的稳定偏好。
- 用户能查看、纠正和删除记忆，删除后立即停止召回。
- 评测中错误记忆率、无关召回率达到项目设定阈值。

### 阶段 4：RAG、MCP 与 Agent 可靠性，预计 1 周

#### 阶段目标

将当前“可以调用”的 RAG、MCP 和 Agent 提升为可更新、可降级、可追踪且适合并发运行的生产级组件。

#### 4.1 RAG 索引生命周期

主要涉及：

- zzx-ai-agent-backend/app/llm/rag.py
- zzx-ai-agent-backend/documents

具体任务：

1. 首次在线查询不再执行完整 Chroma.from_documents。
2. 建立独立索引命令或后台索引任务。
3. 每个源文档记录 source_id、路径、内容哈希、更新时间和索引版本。
4. 每个分块使用稳定 chunk_id，例如 source_id 加内容位置和哈希。
5. 文档新增、修改、删除时只处理受影响分块。
6. 新索引先构建到新版本，验证成功后原子切换 active_version。
7. 保留上一版本，出现质量或兼容问题时快速回滚。
8. 索引构建失败不影响当前线上版本查询。

#### 4.2 中文混合检索

1. 中文 BM25 使用 jieba、pkuseg 或适合业务语料的分词器，不使用简单空格切分。
2. 同时执行向量检索与关键词检索。
3. 使用 Reciprocal Rank Fusion 或归一化分数合并候选。
4. 对候选进行 rerank，再按来源去重和相邻分块合并。
5. 记录每阶段候选数量、分数与耗时。
6. 准备恋爱建议、项目技术文档等典型查询的离线评测集，计算 Recall@K、MRR 或 nDCG。

#### 4.3 引用与可追溯性

每个返回分块携带：

- source_id、source_name
- chunk_id
- 标题或章节
- 文档版本
- 起止位置或页码
- 检索与重排分数

模型回答要求将事实与引用绑定。前端支持点击引用查看来源片段。没有足够证据时应明确说明，而不是伪造引用。

#### 4.4 Reranker 并发与资源

1. 模型加载使用进程内锁，避免多个请求重复加载。
2. 启动阶段可选择预热，避免首请求承担全部延迟。
3. 限制 rerank 批大小和并发数。
4. CPU 密集型推理从 Web 线程隔离。
5. 内存不足时可降级为不重排或使用轻量模型。
6. 记录加载耗时、推理耗时、内存占用和降级次数。

#### 4.5 MCP 客户端生命周期

主要涉及：

- zzx-ai-agent-backend/app/llm/mcp_tools.py
- zzx_mcp_server/server.py

具体任务：

1. 初始化过程增加锁，避免并发请求重复初始化。
2. 复用 MCP 会话、连接和长期事件循环，不为每次同步调用创建新事件循环。
3. 定义启动、健康检查、重连和优雅关闭生命周期。
4. 每个工具设置连接超时、执行超时和最大返回大小。
5. 只对幂等读操作默认重试；写操作必须携带 action_id。
6. 连续失败达到阈值后打开熔断器，在冷却期快速失败或走降级逻辑。
7. 服务恢复后使用少量探测请求关闭熔断器。
8. MCP 不可用时，Agent 应说明工具暂不可用，并尽可能完成不依赖工具的回答。

#### 4.6 工具治理

为工具登记元数据：

- name、description、owner
- risk_level
- read_only
- timeout_seconds
- max_retries
- input_schema、output_schema
- result_size_limit
- requires_confirmation

执行规则：

- 读取型低风险工具可自动调用。
- 有外部写入或不可逆影响的工具必须先确认。
- 写入型工具使用 action_id 和执行记录防止重复。
- 工具输出先校验 schema，再进入模型上下文。
- 超大结果存储为引用，只把摘要和必要片段传给模型。

#### 4.7 Agent 运行控制

主要涉及：

- zzx-ai-agent-backend/app/llm/agent.py
- zzx-ai-agent-backend/app/llm/chain.py
- zzx-ai-agent-backend/app/llm/skill_middleware.py

具体任务：

1. 设置最大迭代次数、最大工具次数、单次和总运行超时。
2. 限制同一工具的重复调用次数，检测无进展循环。
3. 将原始 Thought 输出替换为安全状态：
   - 正在理解问题
   - 正在检索资料
   - 正在调用某工具
   - 正在整理结果
4. 保存工具名称、耗时、成功状态和经过清洗的摘要，不保存隐藏推理内容。
5. 工具返回不可信文本时按数据处理，不能让其覆盖系统指令。
6. Agent 失败时保留已完成步骤，返回可恢复的错误码。
7. 对不同问题进行路由：普通问答优先 Chain，需要行动时才进入 Agent，知识问题才调用 RAG。

#### 测试重点

- 文档增加、修改和删除后只更新对应分块。
- 新索引构建失败时查询仍使用旧版本。
- 中文关键词和语义改写查询都能召回正确来源。
- 50 个并发请求不会重复加载 reranker 或 MCP 客户端。
- MCP 超时、断开和返回错误 schema 时能够熔断或降级。
- Agent 遇到循环工具结果时在上限内停止。
- 所有 RAG 引用都能定位到真实文档分块。

#### 阶段交付物

- 独立增量索引流程和索引版本表。
- 中文混合检索、重排及离线评测。
- 引用数据结构和前端引用展示。
- MCP 生命周期、重试、熔断和工具注册中心。
- Agent 路由、运行上限和安全状态事件。

#### 验收标准

- 更新知识库不需要重启 API，失败可回滚到旧索引。
- MCP 服务不可用时主对话可控降级，不产生永久挂起任务。
- Agent 不向用户输出隐藏推理或内部异常。
- RAG 答案引用可点击、可追溯，核心评测指标优于当前基线。

### 阶段 4.5：多 Agent 协作与 A2A 演进，预计 1 至 2 周

#### 阶段结论

当前项目第一版多 Agent 不直接引入 A2A 协议，优先使用“内部任务图 + Redis Worker + 统一 AgentRuntime 接口”完成协作。

原因：

- 初期各 Agent 运行在同一个 Python 后端中。
- 各 Agent 共用 MySQL、Redis、模型、RAG、MCP 和用户记忆。
- 当前核心需求是任务拆分、依赖调度、并发控制、幂等、预算和结果合并。
- A2A 主要解决相互独立、跨服务、跨框架或跨组织 Agent 之间的发现与通信，并不负责内部编排。
- 过早引入 A2A 会增加 Agent Card、远程认证、网络调用、协议状态映射和双层重试等复杂度。

架构应预留 A2A 适配层，使未来接入远程 Agent 时无需重写协调器。

#### 4.5.1 推荐协作结构

~~~text
用户问题
  -> 路由器：判断单 Agent 或多 Agent
  -> 协调 Agent：创建受控任务图
       -> 专业 Agent A
       -> 专业 Agent B
       -> 工具 Agent
  -> 评审 Agent：检查冲突、遗漏和风险
  -> 汇总 Agent：生成唯一最终回复
~~~

基本原则：

1. 简单问题继续使用单 Agent，避免不必要的延迟和 Token 消耗。
2. 只有没有依赖关系的分析任务才能并行。
3. 最终消息只由汇总 Agent 写入。
4. 专业 Agent 返回结构化结果，不互相传递完整隐藏推理。
5. 外部写操作不能被多个 Agent 并行执行。
6. 用户取消主 run 后，所有尚未完成的子任务都应停止或进入取消状态。

#### 4.5.2 恋爱助手 Agent 角色

第一版建议包含：

- intent_router：识别咨询类型、复杂度和用户期望，决定是否启用多 Agent。
- emotion_analyst：分析对话中明确表达的情绪、关系状态和可能误解，不进行无证据心理诊断。
- communication_strategist：给出沟通时机、边界、行动步骤和备选方案。
- message_writer：根据分析结果生成道歉、沟通、表白等候选文案。
- safety_reviewer：检查骚扰、控制、PUA、操纵、过度推断和其他不健康建议。
- answer_synthesizer：消除冲突，合并专业结果并输出最终回答。

典型流程：

~~~text
                 -> emotion_analyst ---------
intent_router    -> communication_strategist -> safety_reviewer -> answer_synthesizer
                 -> message_writer ----------
~~~

“帮我写一句晚安”一类简单请求直接交给 message_writer；“伴侣长期回避沟通，我该如何判断和处理”一类复杂请求才启动完整协作。

#### 4.5.3 通用 Agent 角色

- planner：拆分任务，生成依赖明确的任务图。
- researcher：调用 RAG 或其他只读数据源。
- tool_executor：统一执行 MCP 与受控工具。
- analyst：分析检索和工具结果。
- reviewer：检查准确性、引用、遗漏和安全风险。
- writer：生成最终交付结果。

通用 Agent 不应默认启动所有角色。路由器根据问题类型选择最少角色集合。

#### 4.5.4 AgentRuntime 抽象

协调器不直接依赖某个 Agent 框架或 A2A SDK，先定义内部接口：

~~~python
class AgentRuntime:
    def execute(self, task, context):
        ...

    def cancel(self, task_id):
        ...

    def get_status(self, task_id):
        ...
~~~

实现分为：

- LocalAgentRuntime：调用当前项目内部 Agent。
- A2AAgentRuntime：未来通过 A2A 调用远程 Agent。

调用侧保持一致：

~~~python
result = runtime.execute(task, context)
~~~

这样可以先完成本地协作，未来只增加 A2A 适配器，不改动协调器、任务表和上层业务流程。

#### 4.5.5 受控任务图

协调 Agent 只生成结构化计划：

~~~json
{
  "tasks": [
    {
      "key": "emotion_analysis",
      "agent": "emotion_analyst",
      "depends_on": []
    },
    {
      "key": "reply_draft",
      "agent": "message_writer",
      "depends_on": ["emotion_analysis"]
    },
    {
      "key": "safety_review",
      "agent": "safety_reviewer",
      "depends_on": ["reply_draft"]
    }
  ]
}
~~~

后端必须验证模型生成的任务图：

- Agent 名称必须存在于注册白名单。
- 第一版每个 run 最多 5 个子任务。
- 最大依赖深度为 3。
- 禁止循环依赖和不存在的依赖。
- 最大重新规划次数为 1。
- 每个任务必须配置超时和 Token 上限。
- 任务输入只能引用批准的上下文与前置任务输出。
- 高风险工具不能通过计划文本绕过确认流程。

#### 4.5.6 数据模型

在 chat_runs 基础上新增 agent_tasks：

- id、run_id、parent_task_id
- task_key、agent_name、task_type
- status：pending、ready、running、succeeded、failed、cancelled、timed_out
- depends_on 或独立依赖表
- input_json、output_json、error_code
- attempt、worker_id、locked_until、heartbeat_at
- prompt_tokens、completion_tokens、estimated_cost
- created_at、started_at、finished_at

唯一约束：

- run_id、task_key

该约束保证协调器、队列或 Worker 重试时不会重复创建相同子任务。

agent_task_dependencies：

- task_id
- depends_on_task_id
- 两个字段组成唯一约束

agent_events：

- event_id、run_id、task_id
- agent_name、event_type
- safe_summary、created_at

agent_artifacts：

- id、run_id、task_id
- artifact_type、content_ref
- mime_type、metadata_json
- created_at

大文本、文件和结构化交付物保存为 Artifact 引用，不重复塞入所有 Agent 的上下文。

#### 4.5.7 状态与调度

子任务状态：

~~~text
pending -> ready -> running -> succeeded
                           -> failed
                           -> cancelled
                           -> timed_out
~~~

调度规则：

1. 创建任务图后，只有依赖全部成功的任务进入 ready。
2. Worker 通过原子条件更新领取任务。
3. 前置任务失败时，下游任务进入 blocked 或由协调器决定降级。
4. 同一个 task_key 的重试复用原任务记录并增加 attempt。
5. 只读分析任务可以并行，最终汇总和会话写入必须串行。
6. 主 run 只有在所有必需任务完成并成功写入最终回复后才能 succeeded。
7. 任何子任务超时都必须传播为明确状态，不能让主 run 永久停留在 running。

建议初始限制：

- 单个 run 最多同时运行 3 个 Agent。
- 单个用户最多同时运行 2 个多 Agent run。
- 单个 run 最多 5 个子任务。
- 最大重新规划次数为 1。
- 最大总运行时间为 120 秒。
- 每个 Agent 分配独立 Token 上限，总 run 再设置总预算。

#### 4.5.8 上下文与记忆边界

- 每个 Agent 只获取完成当前任务所需的最小上下文。
- 子 Agent 之间通过结构化 output_json 或 Artifact 共享结果。
- 用户长期记忆默认对专业 Agent 只读。
- 只有 Memory Curator 可以提出记忆候选。
- 记忆候选仍需经过敏感性、置信度、去重和冲突检查。
- RAG 文档和工具结果不能直接写成用户长期记忆。
- Agent 私有草稿不进入会话历史。
- 最终会话只保存用户消息、最终回答和安全的执行摘要。

共享状态可以包括：

~~~json
{
  "user_goal": "修复关系并准备道歉",
  "constraints": ["不希望显得敷衍"],
  "agent_results": {
    "emotion_analysis": {},
    "communication_plan": {},
    "message_draft": {}
  }
}
~~~

#### 4.5.9 工具权限

- 分析 Agent 默认不能执行外部写操作。
- researcher 只能使用 RAG 和批准的只读工具。
- tool_executor 负责所有 MCP 工具调用。
- 写入型工具必须携带 action_id，并记录幂等执行结果。
- 高风险操作必须等待用户确认。
- reviewer 只能审核，不能代替 tool_executor 执行操作。
- 工具返回内容视为不可信数据，必须校验 schema 和大小。

MCP 与 A2A 的职责边界：

~~~text
A2A：独立 Agent 与独立 Agent 之间通信
MCP：Agent 调用工具、数据源和外部能力
~~~

A2A 不替代 MCP。未来远程 Agent 内部仍然可以通过 MCP 使用工具。

#### 4.5.10 成本与性能

多 Agent 会显著增加模型调用次数，因此需要：

1. 路由器判断是否真的需要协作。
2. 子 Agent 使用精简提示词和最小上下文。
3. 子 Agent 返回结构化结论，不生成完整长文。
4. 只有 answer_synthesizer 生成面向用户的完整回答。
5. 分类、摘要和评审可使用成本较低的模型。
6. 为每个任务和总 run 同时设置 Token、时间和费用预算。
7. 达到预算时停止新增任务，使用已有结果降级汇总。

需要监控：

- 单 Agent 与多 Agent 的启用比例。
- 每个角色的延迟和 Token。
- 总运行成本和首个状态事件时间。
- 子任务成功率、重试率和超时率。
- 重新规划次数与循环拦截次数。
- 专业 Agent 之间的冲突率。
- 多 Agent 相对单 Agent 的质量提升。

#### 4.5.11 A2A 引入条件

满足以下任一明确需求时再正式引入：

- Agent 被拆分成独立服务或部署在不同机器。
- 需要调用其他语言或其他团队维护的 Agent。
- 需要接入第三方 Agent 平台。
- 需要通过 Agent Card 动态发现远程能力。
- 要把恋爱助手或通用 Agent 开放给外部系统调用。
- 跨组织长任务需要统一的查询、流式状态、取消或推送协议。

届时映射关系为：

| 内部模型 | A2A 概念 |
| :--- | :--- |
| agent_definition | Agent Card |
| agent_task | Task |
| agent_message | Message |
| agent_event | Task 状态更新 |
| agent_artifact | Artifact |
| agent_skill | Agent Skill |

A2A 接入安全要求：

- 远程 Agent 地址必须来自允许列表，避免 SSRF。
- Agent Card 和远程响应一律视为不可信输入。
- 认证凭据只放 HTTP Header，不放任务消息。
- 用户身份不能原样转发，使用最小权限的服务身份或委托令牌。
- 本地 run_id 与远程 task_id 建立唯一映射。
- 本地重试必须复用远程 task_id，避免重复创建任务。
- 远程 Agent 返回的 Artifact 必须校验类型、大小和下载地址。
- 为每个远程 Agent 设置超时、熔断、调用预算和审计记录。

官方规范参考：

- https://a2a-protocol.org/latest/specification/
- https://github.com/a2aproject/A2A

#### 4.5.12 分步实施

第一步，阶段 2 同步预留：

- 完成 chat_runs、Redis Worker、可靠 SSE、幂等、取消和恢复。
- 在数据库迁移中预留 agent_tasks 与任务依赖关系。
- 定义 AgentRuntime、AgentTask、AgentResult、AgentArtifact 接口。

第二步，阶段 4 后实现内部 MVP：

- 使用固定任务图。
- 只实现 intent_router、emotion_analyst、communication_strategist、message_writer、safety_reviewer 和 answer_synthesizer。
- 不允许模型动态创建任意角色。
- 不允许递归委派。
- 使用特性开关，仅对复杂咨询启用。

第三步，验证后增强：

- 引入动态但受验证的任务图。
- 增加通用 Agent 的 planner、researcher、tool_executor、reviewer 和 writer。
- 增加运行时间线、成本展示和人工确认节点。

第四步，阶段 6 按需加入 A2A：

- 实现 A2AAgentRuntime 适配器。
- 先接入一个受信任的远程测试 Agent。
- 再考虑将本项目 Agent 暴露为 A2A Server。
- 使用协议一致性测试和故障注入验证兼容性。

#### 测试重点

- 简单问题不会错误启动多 Agent。
- 独立任务能并行，有依赖任务严格按顺序执行。
- 同一个子任务重复投递不会重复执行。
- 任务图中的循环、未知 Agent 和超限任务被拒绝。
- 单个 Agent 失败时能降级汇总或明确失败。
- 用户取消后所有子任务最终进入终态。
- 任何 Agent 都不能绕过工具权限和用户确认。
- 多 Agent 不会重复或冲突写入长期记忆。
- 前端只显示安全步骤状态，不显示隐藏推理。
- 在固定评测集上，多 Agent 质量提升足以覆盖增加的延迟和成本。

#### 阶段交付物

- AgentRuntime 与本地运行适配器。
- Agent 注册表、角色权限和模型配置。
- agent_tasks、依赖、事件与 Artifact 数据结构。
- 任务图验证器和协调器。
- 恋爱助手多 Agent MVP。
- 前端协作时间线与取消状态。
- 单 Agent 对比多 Agent 的质量、延迟和成本报告。
- A2A 适配设计文档，不在 MVP 中强制实现。

#### 验收标准

- 简单任务继续走单 Agent，复杂任务才触发协作。
- 多 Agent run 可查询、可取消、可恢复且不会重复执行。
- 不出现无限委派、循环依赖或无限工具调用。
- 最终回答只写入一次，并能追溯所使用的专业结果。
- 多 Agent 的总时间、Token 和费用不超过设定预算。
- 第一版内部多 Agent 不依赖 A2A，但远程 Agent 可通过新增适配器接入。

### 阶段 5：前端交互、测试、可观测性与部署，预计 1 周

#### 阶段目标

在已有视觉优化基础上补齐复杂运行状态、工程质量、故障定位和可重复部署能力。

#### 5.1 前端状态管理

具体任务：

1. 使用 Pinia 或统一组合式状态层管理用户、会话、消息、run 和记忆。
2. API 客户端统一注入 Token、request_id，并处理 401、403、409、429 和 5xx。
3. 访问令牌过期时执行一次受控刷新；刷新失败统一退出登录。
4. API Base URL 使用 import.meta.env 环境变量。
5. 消息模型增加 client_message_id、run_id、status、error 和 retryable。
6. 区分“重新连接原任务”和“创建新的重新生成任务”。
7. 会话与消息使用游标分页；消息很多时采用虚拟列表。
8. 页面切换后保留未完成任务，不因组件卸载丢失状态。

#### 5.2 关键交互完善

- 停止生成。
- 失败重试。
- 重新生成。
- 编辑用户消息后从该位置创建分支。
- 复制回答和引用。
- 工具执行时间线。
- 排队、限流、断网、恢复和降级提示。
- 空状态、骨架屏和局部错误状态。
- 记忆查看与删除。

无障碍要求：

- 键盘可完成核心操作。
- 输入框、按钮、弹窗有清晰 aria 标签。
- 颜色不是唯一状态提示。
- 流式新增内容不会持续抢夺屏幕阅读器焦点。

#### 5.3 自动化测试体系

后端建议使用 pytest：

- config、JWT、资源归属和输入校验单元测试。
- 会话、消息、run、取消和分页接口测试。
- 数据库事务、死锁重试和幂等并发测试。
- Token 预算、摘要水位、记忆抽取和召回测试。
- RAG 检索、MCP 降级和 Agent 上限测试。
- SSE 事件顺序、断线续传和终态测试。

前端建议使用 Vitest 与 Vue Test Utils：

- Store 状态转换。
- API 错误映射。
- 流事件合并与去重。
- 取消、重试和页面恢复。
- Markdown 安全渲染。

端到端测试覆盖：

- 注册、登录、创建会话、发送消息、接收流。
- 刷新页面后恢复任务。
- 删除会话和删除记忆。
- Token 过期和无权限访问。

所有外部模型、天气接口、MCP 和向量服务提供 Mock 或 Fake，默认测试不消耗真实 Token。

#### 5.4 日志、指标与追踪

结构化日志字段：

- timestamp、level、service、environment
- request_id、trace_id、run_id
- user_id、session_id
- route、event、duration_ms
- error_code

敏感字段只记录摘要或哈希。不要记录 Authorization、完整提示词、完整工具响应和隐藏推理。

核心指标：

- API 请求量、错误率、P50、P95、P99。
- 首 Token 时间和完整回答时间。
- 活跃 SSE 连接数与断线重连次数。
- 队列长度、排队时间、Worker 使用率和任务终态分布。
- 数据库连接池使用率、慢查询和事务回滚。
- 模型 Token、估算成本、限流和超时。
- Agent 迭代数、工具成功率、MCP 熔断次数。
- 摘要触发、成功率、延迟和压缩率。
- 长期记忆抽取、召回、编辑和删除次数。
- RAG 检索耗时、无结果率和引用覆盖率。

告警建议：

- 5xx 错误率持续超过阈值。
- P95 首 Token 时间显著上升。
- 队列堆积或最老任务等待过久。
- running 任务无心跳。
- 数据库连接池接近耗尽。
- 模型或 MCP 连续超时。

#### 5.5 健康检查

- /livez：进程是否存活，不依赖外部服务。
- /readyz：数据库、Redis 和必要初始化是否可用。
- /health/details：仅内部网络访问，显示组件状态与版本。

Kubernetes 或 Docker 编排只根据 livez 决定是否重启，根据 readyz 决定是否接收新流量，避免第三方 API 短暂异常造成整个服务反复重启。

#### 5.6 部署与 CI

具体任务：

1. 提供 Docker Compose，包含前端、API、Worker、MySQL、Redis 和可选 MCP。
2. 所有镜像使用固定版本，不依赖 latest。
3. 提供开发、测试和生产环境变量说明。
4. 修正 zzx-ai-agent-frontend/nginx.conf 中写死的上游地址。
5. Nginx 为 SSE 单独配置 proxy_buffering off、合理超时和缓存控制。
6. 前端使用多阶段构建，最终镜像只保留静态资源。
7. 后端使用非 root 用户运行。
8. 服务启动前运行数据库迁移，但避免多个副本同时迁移。

CI 流程：

~~~text
代码检查
  -> 后端和前端测试
  -> 数据库迁移验证
  -> 前端构建
  -> 依赖漏洞与密钥扫描
  -> 构建镜像
  -> 测试环境冒烟测试
~~~

#### 测试重点

- 从空环境按文档启动整套服务。
- 前端构建和路由刷新正常。
- Nginx 下 SSE 不被缓冲且心跳有效。
- 通过 run_id 能串联 API、Worker、模型和工具日志。
- 数据库、Redis、模型或 MCP 分别不可用时告警和降级符合预期。
- CI 能阻止测试失败、迁移冲突和密钥泄露。

#### 阶段交付物

- 完整前端运行状态与错误交互。
- 后端、前端和端到端自动化测试。
- 指标面板、日志查询模板和告警规则。
- Docker Compose、部署说明和 CI 工作流。
- 当前环境性能基线和容量建议。

#### 验收标准

- 任意失败任务可以通过 run_id 定位完整链路。
- 核心流程拥有稳定自动化回归测试。
- 新机器能够按文档一次启动完整环境。
- 发布前自动检查测试、迁移、依赖风险和敏感信息。

### 阶段 6：产品功能升级与业务扩展，持续迭代

#### 阶段目标

在底层可靠性完成后扩展用户价值。每项功能都应复用 run、幂等、权限、审计和成本控制能力，避免重新形成独立且不可观测的调用链。

#### 6.1 用户知识库

- 支持 PDF、Markdown、Word 和文本上传。
- 显示解析、分块、索引和失败进度。
- 支持文档版本、重新索引和删除。
- 回答展示引用，点击查看原文片段。
- 用户数据按租户隔离，索引和对象存储都校验归属。
- 上传内容进行病毒扫描、类型校验和提示词注入防护。

#### 6.2 Agent、模型、技能和工具中心

- 用户选择普通对话、恋爱助手或通用 Agent。
- 管理每类 Agent 可用的工具、最大步骤和预算。
- 模型按质量、速度和价格路由。
- Skills 显示用途、版本、输入要求和权限。
- 高风险工具调用前展示将要执行的动作并请求确认。
- 每次运行保存使用的模型、提示词版本、Skill 版本和工具版本。

#### 6.3 对话增强

- 停止生成、重新生成、继续生成。
- 编辑历史消息后建立分支，不覆盖原对话链。
- 多答案对比。
- 会话置顶、搜索、标签、归档和导出。
- 分享只生成只读快照，并支持撤销和过期。
- 回复中的代码、表格和引用提供专门交互。

#### 6.4 反馈与评测闭环

1. 点赞、点踩后允许选择原因。
2. 收集是否有帮助、是否准确、是否引用错误、是否工具失败。
3. 将匿名或授权样本进入离线评测集。
4. 每次修改 Prompt、模型、RAG 或记忆策略前后运行同一评测。
5. 按版本比较正确率、延迟、Token 和成本。
6. 低质量样本进入人工复核，不直接用用户反馈自动修改长期记忆。

#### 6.5 成本与模型路由

- 简单问答使用低成本模型，复杂 Agent 使用更强模型。
- 摘要、记忆抽取和查询改写使用独立小模型。
- 对完全相同且不含私人上下文的安全请求考虑缓存。
- 设置用户级和系统级 Token、调用次数和成本预算。
- 超预算时降级模型、缩短检索数量或提示用户。
- 管理端展示按模型、Agent、用户和功能划分的成本。

#### 6.6 多模态

- 图片理解与图片消息。
- 语音转文字和回复朗读。
- 文件阅读与结构化抽取。
- 多模态内容仍使用统一 message、run 和 attachment 数据模型。
- 文件处理放在独立任务队列，并进行大小、格式和安全校验。

#### 6.7 管理与多租户

- 用户、角色、配额和封禁管理。
- 工具调用、敏感操作和配置变更审计。
- 租户级数据隔离、密钥配置和模型预算。
- 运营数据只展示聚合指标，默认不直接暴露私人对话。
- 支持数据导出和删除请求。

#### 6.8 模板与定时任务

- 常用咨询模板、提示词模板和 Agent 工作流模板。
- 经过用户明确授权后创建定时任务。
- 定时任务也使用 run 模型，具备幂等键、超时、重试、取消和审计。
- 涉及外部写操作时，每次执行前按风险级别确认或使用明确的长期授权。

#### 产品阶段验收原则

- 新功能必须接入统一鉴权和资源归属。
- 所有外部写操作必须可审计并防止重复执行。
- 所有模型任务必须存在 run 状态、超时和成本记录。
- 用户数据必须可查看、导出和删除。
- 功能上线前必须有离线评测、灰度指标和回滚开关。

## 6. 推荐里程碑与排期

### 6.1 个人项目或作品集版本

建议优先用 4 至 6 周完成阶段 0 至阶段 3：

- 第 1 周：阶段 0，加上阶段 1 的迁移框架和基础表结构。
- 第 2 周：完成阶段 1，消息幂等、任务状态、事务和分页可用。
- 第 3 至 4 周：完成阶段 2，异步 Worker、可靠 SSE、取消和恢复可用。
- 第 5 至 6 周：完成阶段 3，动态上下文、增量摘要和长期记忆最小版本可用。

这一版本已经能充分展示安全设计、并发处理、分布式任务、流式协议和 AI 记忆系统等核心能力。

### 6.2 完整工程版本

- M1 安全基线：密钥轮换、统一鉴权、输入安全、生产配置。
- M2 数据正确性：迁移、事务、连接池、消息顺序和分页。
- M3 可靠请求：幂等键、chat_run、任务查询和取消。
- M4 并发架构：Redis、Worker、事件流、恢复和限流。
- M5 记忆 2.0：Token 预算、摘要水位、长期记忆和用户控制。
- M6 AI 可靠性：增量 RAG、引用、MCP 熔断和 Agent 运行上限。
- M7 多 Agent MVP：内部任务图、角色协作、评审、预算和运行时间线。
- M8 工程交付：测试、观测、告警、CI 和可重复部署。
- M9 产品升级：知识库、配置中心、反馈、成本和多模态。
- M10 A2A 演进：仅在出现跨服务或第三方 Agent 需求时实现 A2A 适配器。

## 7. 推荐任务拆分

为了降低一次性改造风险，每个阶段继续拆成可独立合并的变更：

1. 每个变更只解决一个主题，例如“统一资源鉴权”或“新增 chat_runs”，不要把安全、数据库和 UI 全部放进一个提交。
2. 数据库变更先合并迁移，再合并读取兼容，最后切换写入逻辑。
3. 新旧聊天接口保留短暂兼容期，通过配置开关逐步切流。
4. 新记忆系统先影子运行，只记录评测结果，不立刻影响回答；验证后再启用召回。
5. 新 RAG 索引使用版本切换，不直接覆盖现有索引。
6. Redis 或 Worker 不可用时提供明确降级开关，便于本地开发和紧急回退。
7. 每个任务必须包含测试、文档、监控指标和回滚说明。

## 8. 实施约束与决策原则

- 每个阶段先定义数据和接口契约，再修改实现。
- 每次数据库结构变化都必须提供升级、数据校验和回滚说明。
- 外部模型与工具调用必须设置超时、并发上限、重试边界和失败降级。
- 写操作只有在已经具备幂等性后才允许自动重试。
- 性能优化必须通过压测数据验证，不能以“增加线程数”作为唯一结论。
- 用户之间的资源隔离必须由后端和数据库查询保证，不能依赖前端隐藏。
- 长期记忆遵循最少保存、来源可追溯、过期可配置、用户可修改和删除。
- RAG 文档、工具结果和用户记忆都视为不可信数据，不能覆盖系统安全规则。
- 不对用户展示隐藏推理，只展示安全、可核验的步骤状态和工具结果。
- 新功能必须具备关闭开关和回退路径。
